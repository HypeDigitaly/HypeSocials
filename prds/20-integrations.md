# 20 — Integrations

Covers every external system HypeSocials talks to: how it connects, what it fetches or submits, and how it fails safely. Cross-references: `00-overview.md` for the pipeline stages that call these integrations, `30-configuration-and-run.md` for config file structure, `10-pipeline.md` for the analyze/write/generate stages that consume this data, `40-outputs-and-logging.md` for run logging of every call made here.

Requirement ranges owned by this file: **FR-30–FR-49**, **FR-110–FR-129**, **FR-160–FR-169**, **FR-240–FR-249**, and **FR-270–FR-279** (FR-130+ belongs to `30-configuration-and-run.md`, so this file's post-review extensions ran to FR-169 and continue in the fresh FR-240 block; the FR-270 block carries the v1.5 render-provider seam, Section 12 — FR-270–FR-273 used, FR-274–FR-279 held for this file's future provider/profile work); NFR-10–NFR-14, NFR-110–NFR-112, NFR-160.

Config key names used below (`poll_interval_s`, `mcp_startup_timeout_s`, `http_max_attempts`, `mcp_call_timeout_s`, and the rest) are **defined canonically in `30-configuration-and-run.md`** — this file references them by name and states the behaviour they govern; it does not own their defaults.

## TL;DR — Plain English

HypeSocials talks to five outside systems, split into two clean groups.

**Content systems** — Virlo (trend data), Notion (brand info), and later Postiz (scheduling) — are things that *hold* content, so the engine talks to them through **MCP**, a standard way for an AI app to call another program's tools. Virlo doesn't have an official MCP server, so HypeSocials ships its own tiny one, written in plain Python, that just translates Virlo's normal web API into five MCP tools — no caching, nothing fancy. One of those five simply lists the available monitors by name and id, so setting the app up the first time doesn't depend on hunting for numbers in a dashboard. Notion has a real MCP server too, but HypeSocials uses the simple "paste a token" version, not the one that needs a browser login, because runs happen unattended overnight. Postiz, coming in the next phase, is the one exception: its official AI-connector (MCP) genuinely cannot accept the image/video files this app creates, so drafts get pushed to Postiz over its plain web API instead — MCP is only used there for small lookups, not for publishing. The full Postiz plan lives in `60-publishing-postiz.md`; this file states the honest transport facts.

**Model APIs** — OpenRouter (the AI brains that analyze trends and write copy) and Kie.ai (the service that renders images and reels) — are just plain web calls. Reels come back with AI-generated sound built in, and before rendering a reel the engine downloads a copy of the trend's actual winning video so the renderer can copy its motion, not just a still image. Model APIs don't hold state between calls, so wrapping them in MCP would add nothing but slowdown.

**Models can be swapped by editing a text file, not the engine.** Every model name — the analyzing brain, the copywriter, the image model, the reel model — lives in the config file, and both model services accept whichever model you name through the same door, so moving to a newer or cheaper model of the same kind is a one-line edit. Talking to a rendering service happens through one small doorway with exactly four jobs: send work, ask if it's done, collect the finished links, and turn a file on the operator's computer into a link. Kie.ai is the only service plugged into that doorway today. Each render model also carries a short note saying what it calls its own settings and which prompt style it likes, so adding a completely new model family later means writing that note plus a set of prompts — not rebuilding the engine. Name a model the engine has no note for and the run stops before spending a cent, saying exactly which note is missing. Higgsfield.ai was researched as a second rendering service and turned down for now: it doesn't have the reel model this app depends on, and its AI-connector insists on a human logging in — which an unattended overnight run cannot do.

**The big "check this first" question has been answered.** This whole product is built on showing the image model the actual winning pictures and saying "make something like this." Live verification (2026-08-09) confirmed Kie really does accept reference pictures — just on a sibling route of the one this file originally named: reference-bearing jobs go to the image-to-image route (up to 16 picture links per job), and only picture-less fallback jobs use the text-only route. Everything the engine sends to the image model is written out field by field in this file, nearly all of it now marked *confirmed*; the one remaining first-day check is a single cheap render proving the model actually copies the style of the pictures it is shown.

Pictures that live on the operator's own computer (the Inspiration folder, a campaign brief's own images) can't be handed to a renderer as a local file — the renderer only understands web links. So they get uploaded first, through the same upload door the trend videos use, and the link that comes back is what gets attached.

Every connection is built to fail small: if Virlo hiccups, that one trend is skipped, not the whole run; if Notion is unreachable, brand context is simply left out; if an image job gets stuck, that one image is skipped and the rest keep going; if one of three reference pictures won't download, the job runs with two. A render job that reports "success" but hands back nothing usable is counted as a failure, not a win — a happy status code with an empty result is still an empty result. Temporary files the engine downloads along the way are tidied up when the run ends; the finished-output folder is the only thing that is never touched. Where source data feeds the engine at all (Virlo today; Google Trends or Hacker News someday), it's plugged in through one small, swappable "source adapter" shape, so adding a new source later doesn't mean rewriting the engine.

One more thing on secrets: none of the API keys this file describes are ever shown to an AI model or written into a log file — they only ever travel inside web-request headers or a server's private environment, and anything key-shaped is scrubbed if it ever gets near a log.

## 1. Integration philosophy

HypeSocials draws a firm line between two kinds of external dependency, per **D1**:

- **Content services** — systems that hold or accept structured content (trend intelligence, brand knowledge, scheduling): **Virlo**, **Notion**, and (Phase 2) **Postiz**. Connected through **real MCP servers** wherever the server can actually do the job. The engine is a genuine async MCP client, not a REST client pretending to speak MCP.
- **Model inference APIs** — systems that take a prompt/payload and return a generation: **OpenRouter** and **Kie.ai**. Called **direct REST** over `httpx`. There is no protocol benefit to wrapping a stateless inference call in MCP.

This split is deliberate and permanent — it is not "MCP everywhere" and not "REST everywhere," it is the right transport for the right job. **Postiz is the one documented exception inside "content services":** its official MCP server has no way to ingest externally generated media (Section 6), so the load-bearing publishing path for HypeSocials' own creatives runs over Postiz's public REST API, with MCP kept only as an optional ops-query seam. This was discovered by verifying Postiz's actual tool surface (see D1, D29) — it is a fact about one vendor's API, not a reversal of the MCP-for-content-services principle, which still holds cleanly for Virlo and Notion.

- **FR-30**: The engine SHALL implement one shared async MCP client used by all MCP-backed integrations (Virlo, Notion, and Postiz's optional ops-query seam — Section 6), configured per-server via launch command/URL and transport type.
- **FR-31**: The engine SHALL open MCP sessions for the integrations a run actually needs at the start of Collect, and close all open sessions before the run ends, regardless of run outcome.
- **NFR-10**: All integration calls (MCP tool/resource calls and REST calls alike) SHALL run concurrently wherever the pipeline stage allows it (per **D5** — see FR-42, FR-43), never serialized unless a genuine data dependency requires it.

## 2. MCP client layer (shared plumbing)

One async MCP client module, built on the official Python MCP SDK, is shared by every MCP-backed integration. It does not hardcode per-server logic beyond mapping tool calls — each server's transport, launch command, and environment come from config (full schema and a worked example live in `30-configuration-and-run.md`; HTTP-transport entries additionally carry an `auth_env` field naming the environment variable that holds that server's bearer token).

**Windows-safe launch.** Two Windows-specific traps are handled explicitly: (1) npm-installed CLI tools install as `.cmd`/`.exe` shims, not bare executables, so the launcher resolves the actual shim path or launches via `cmd /c` rather than assuming a direct exec works; (2) a subprocess tree (e.g. `npx` spawning a further Node process) is fully terminated on every exit path — success, failure, timeout, or abort — via Windows job objects or an explicit `taskkill /T` sweep. A dangling MCP subprocess after a run is a bug, not a cosmetic issue.

**Per-server environment.** Each stdio server receives an explicit, minimal environment dict — only the variables that server needs, named per server in config (the Virlo wrapper gets `VIRLO_API_KEY` and nothing else; the Notion server gets `NOTION_TOKEN` and nothing else) — not the engine's full process environment forwarded wholesale.

**Timeouts, pinning, and preflight.** MCP server startup has its own configurable timeout, `mcp_startup_timeout_s` (default **20**), separate from the per-tool-call timeout, `mcp_call_timeout_s` (default **30**) — a slow-starting server and a slow individual call are different failure signatures, logged differently. Both keys are defined canonically in `30-configuration-and-run.md`. Server packages are pinned to a specific version and pre-installed (during `run.bat` bootstrap or documented setup), never resolved fresh from a registry on every run via a bare `npx pkg@latest`. A **Node/npx pre-flight check** runs only when a configured server command actually invokes `npx` or `node` — the Virlo wrapper (pure Python) never triggers it.

**Session lifecycle.** A session opens only for integrations a run actually needs, at the start of Collect, and closes as soon as its data has been fully fetched — for Virlo and Notion, that's the end of Collect. The one exception is **Postiz** (Phase 2, `--publish` runs only), whose session opens later, at the publish step.

**Serialization and how concurrency is actually obtained.** Tool calls within a single session are serialized (one in flight at a time) unless a server is specifically documented as concurrency-safe. Concurrency across different monitors/trends/creatives therefore comes from running **several independent sessions**, never from racing calls on one session. Because a stdio session is a subprocess, "several" must be a **bounded, named number** — the per-integration session pool (Virlo's is specified in Section 3) — never one process per work item. Unbounded subprocess spawning is a defect, not a speed-up.

Tool names are **not** config-mapped. The engine's only stdio servers are ones this project ships or pins, so the tool contract is fixed at the code level; the swap path to a different server implementation is still a config edit, but it is a change of *command/URL*, not of tool names (see the FR-116 tombstone below).

- **FR-110**: Stdio MCP servers SHALL be launched with an explicit, per-server environment dict (only the variables that server needs) and with Windows-safe process resolution (`.cmd`/`.exe` shim resolution, or launch via `cmd /c`).
- **FR-111**: Subprocess trees for MCP stdio servers SHALL be fully terminated on every exit path (success, failure, timeout, abort). On Windows this SHALL use a **job object with kill-on-job-close** so that even a hard kill of the engine process (Task Manager, console X, shutdown) reaps the tree; `taskkill /T` is the fallback sweep for orderly exits only.
- **FR-112**: MCP server startup SHALL have its own configurable timeout (`mcp_startup_timeout_s`, default 20), distinct from the per-tool-call timeout (`mcp_call_timeout_s`, default 30); both SHALL be sourced from config, never hardcoded.
- **FR-113**: MCP server packages SHALL be pinned to a specific version and pre-installed; no server command SHALL resolve a package fresh from a registry at run time.
- **FR-114**: An MCP session SHALL close as soon as the data it was opened for has been fetched (end of Collect for Virlo and Notion); only the Postiz session (Phase 2, `--publish`) SHALL remain open past Collect.
- **FR-115**: Tool calls within a single MCP session SHALL be serialized unless the server is documented as concurrency-safe for parallel calls; concurrency SHALL be obtained from a bounded pool of independent sessions (FR-246), never from racing calls on one session and never from unbounded subprocess spawning.
- **FR-116** — **withdrawn (v1.4)**; tool names are fixed by the wrapper contract. The swap-path to an official Virlo server remains config-level (point `mcp_servers` at a different command).
- **FR-117**: A Node/npx presence-and-version pre-flight check SHALL run only when a configured server command invokes `npx` or `node`.

## 3. Virlo via MCP

Virlo is the trend-intelligence source and the primary raw material for visual mimicry (see `00-overview.md` "The Pipeline at a Glance", `10-pipeline.md` for how this data is consumed in Analyze/Write/Generate). The engine talks to Virlo exclusively through MCP tool calls — never a raw HTTP call to a Virlo REST endpoint from engine code.

**MVP ships the wrapper (D21 — settles OQ-3; premise updated 2026-08-09).** Virlo now ships an **official MCP server** (`https://dev.virlo.ai/api/mcp/mcp`, server card at `virlo.ai/.well-known/mcp/server-card.json`, ~49 tools, headless `Authorization: Bearer virlo_tkn_…` — no interactive login, so the disqualifier that ruled out Notion-hosted and Higgsfield MCP does **not** apply). Shipping our own wrapper is therefore a **choice, not a necessity**, and the choice stands for three reasons: a five-tool surface is reviewable, the wrapper pins the tool contract against Virlo's API churn (Virlo removed its Orbit/Comet endpoints on 2026-08-03 with days of notice), and a first-party stdio server needs no HTTP-transport auth plumbing. The official server remains the documented swap path (point `mcp_servers.virlo` at its URL). The shipped wrapper: a thin Python MCP server, `python -m hypesocials.virlo_mcp`, built on the official Python MCP SDK, running as a local stdio subprocess **in the same Python virtual environment** as the rest of the engine — no Node toolchain for this or any other first-party server. It internally calls Virlo's REST API (`api.virlo.ai`, Bearer auth via `VIRLO_API_KEY`, delivered through the per-server env dict from Section 2). Its implementation lines count toward the project's G2 line budget — it is engine code, not an exempt dependency.

**Exactly five tools, nothing more.** No speculative extras, no server-side caching layer (every call re-hits Virlo's REST API fresh), no logic beyond field normalization (reshaping REST JSON into the documented tool-return shape — it does not derive, rank, or filter; that stays in the engine's Select stage):

| Tool | Virlo REST endpoint | Returns |
|---|---|---|
| `get_trends` | `GET /v1/trends/digest` | trend/theme name, confidence, video_count, tactics[], why_it_works, timing analysis, connecting threads |
| `get_monitor_analysis` | `GET /v1/agents/{id}` | deeper "why this is working" intelligence for one monitored theme |
| `get_top_videos` | `GET /v1/agents/{id}/videos` | per video: url, views/likes/shares/comments/bookmarks, description, thumbnail_url, publish date, author followers, hashtags, and (when ready) hook_text, text_overlay_content, summary |
| `get_top_slideshows` | `GET /v1/agents/{id}/slideshows` | per slideshow: image_urls[], panel_count, panel_texts[], hook_text, narrative_arc, text_density |
| `list_monitors` | `GET /v1/agents` | the monitors available to this API key: id + human-readable name (plus whatever else the endpoint volunteers, normalized away if not id/name) |

All five endpoint paths are **verified (2026-08-09)** against Virlo's live OpenAPI spec (`api.virlo.ai/openapi.json`): `GET /v1/trends/digest`, `GET /v1/agents`, `GET /v1/agents/{id}`, `GET /v1/agents/{id}/videos`, `GET /v1/agents/{id}/slideshows` all exist as claimed, base `https://api.virlo.ai/v1`, Bearer auth confirmed. **Operational prerequisite:** the Virlo API requires a payment method and a **prepaid deposit** in the Virlo billing dashboard before any call succeeds — recorded in First-Run Setup (`30-…`) and as OQ-19 (per-call pricing unknown, so "preview is $0" claims read precisely as "zero LLM/render spend").

**Trend-item normalization (the join rule).** A *normalized trend item* — the unit Select ranks (`10-…` FR-5/FR-6) — is assembled **one per configured monitor id**: `get_monitor_analysis` supplies the theme name, confidence, `why_it_works` and tactics; `get_top_videos` and `get_top_slideshows` supply the media, hooks, panel texts and engagement numbers for that same monitor. The global `get_trends` digest is fetched once per run and used only to enrich cross-monitor context fields (timing analysis, connecting threads); it never creates trend items of its own. **Dedupe key:** the Virlo agent id; when two monitors surface materially the same theme, both items survive but share a **history key** — the agent id, falling back to a normalized name slug (lowercase, diacritics ASCII-folded, non-alphanumerics hyphenated) — so `trend_history.json` records one entry and reuse accounting cannot double-count one real-world trend.

**Why `list_monitors` exists.** First-Run Setup has to tell the operator which values to put in `virlo_monitor_ids`. Without this tool, the only documented answer is "find them somewhere in the Virlo dashboard" — an instruction this PRD cannot verify and the operator cannot debug. The tool powers the `--list-monitors` CLI action (canonical in `30-configuration-and-run.md`), which opens a Virlo session, prints `id — name` for every monitor the key can see, and exits at $0. It is a setup aid, not a pipeline step: no run stage calls it.

**Terminology.** "Monitor" is HypeSocials vocabulary, not Virlo's: the config key `sources.virlo_monitor_ids` (see `30-`) names the values passed as arguments to `get_monitor_analysis` / `get_top_videos` / `get_top_slideshows`, which map onto Virlo's `/v1/agents/{id}` resource.

**Error translation.** The wrapper translates Virlo's HTTP status codes into distinguishable MCP error types — auth (401/403), rate-limit (429), not-found (404), server error (5xx) — each raised as a distinct class, so engine failure handling (Section 10) can branch by class instead of parsing error text.

**Session and concurrency model.** The wrapper wraps a **stateless REST API** — it holds no cursor, no auth handshake, no per-session server state — so a session is nothing more than a live subprocess. The default is therefore **one session with serialized calls** (FR-115): cheapest, simplest, and correct for the common single-monitor run.

Collect-stage concurrency across **multiple monitor ids** is obtained by opening a **small bounded pool of wrapper sessions** — `virlo_session_pool`, a named small constant, default **3** (key registered in `30-configuration-and-run.md`) — each spawned and torn down under the existing Windows-safe launch and subprocess-tree-kill rules (FR-110, FR-111). Monitors are handed to the pool as work items; the pool never grows with the number of monitors. Three concurrent sessions is enough to hide network latency for a realistic monitor list while keeping the process count reviewable in Task Manager. **One subprocess per monitor id is explicitly forbidden.**

**Retry policy.** Retries/backoff for Virlo tool calls follow the same bounded policy used for OpenRouter and Kie.ai (Sections 7–8): `http_max_attempts` (default **3**, canonical in `30-configuration-and-run.md`) with exponential backoff, never unbounded, never retried for a class (auth, not-found) that a retry cannot fix.

**Reference-image download.** Virlo returns URLs (thumbnail_url, image_urls[]), not bytes, over MCP. The engine downloads the actual images itself via `httpx` directly from Virlo's public CDN, capped at `media_download_cap` images per trend.

**A single dead image is not a failed job.** CDN URLs rot: one 404, one dead host, one image that times out while its siblings arrive fine. Each reference image is downloaded independently, and a per-image failure removes **that image only** — the trend keeps the rest, the download step is not retried past `http_max_attempts` for the failing URL, and the failure is logged with the URL and reason. If the surviving count falls below `reference_images_per_job` (default 3), the render job **still proceeds** with however many it has, including one; the shortfall is logged. Only a trend that ends up with *zero* usable reference images engages the `text_only` handling owned by `10-pipeline.md`.

**Swap path preserved.** If Virlo ever ships an official MCP server, pointing the engine at it is a config change (launch command/URL) — the tool contract above is what any replacement must satisfy.

- **FR-32**: The engine SHALL fetch trend/theme data, top videos, and top slideshows from Virlo exclusively via MCP tool calls.
- **FR-33**: The engine SHALL download reference images via direct HTTP fetch of the CDN URLs returned by Virlo's MCP tools, capped at `media_download_cap` images per trend.
- **FR-118**: The Virlo MCP wrapper SHALL expose exactly the five tools in the table above, with no server-side caching and no logic beyond field normalization.
- **FR-119**: Virlo HTTP status codes SHALL be translated into distinguishable MCP error classes (auth, rate-limit, not-found, server error).
- **FR-120**: Virlo MCP tool-call retries SHALL use the same bounded-retry/backoff policy as OpenRouter and Kie.ai calls (`http_max_attempts`, default 3).
- **FR-245**: The wrapper SHALL expose `list_monitors`, returning each available monitor's id and human-readable name, and the CLI SHALL expose it as the `--list-monitors` action — a $0, setup-only path that opens a Virlo session, prints the list, and exits without entering the pipeline.
- **FR-246**: Collect-stage concurrency across multiple Virlo monitor ids SHALL use a bounded pool of wrapper sessions (`virlo_session_pool`, default 3), each governed by FR-110/FR-111; the engine SHALL NOT spawn one MCP subprocess per monitor id or otherwise scale subprocess count with workload.
- **FR-247**: Reference images SHALL be downloaded per-image and independently; the failure of any single image SHALL remove only that image, SHALL be logged with URL and reason, and SHALL NOT prevent the render job from proceeding with the remaining references even if the surviving count is below `reference_images_per_job`.
- **NFR-11**: The Virlo integration boundary SHALL be a single MCP seam — no code path in the engine SHALL call Virlo's REST API directly.
- **NFR-110**: The Virlo MCP wrapper's implementation lines SHALL count toward the project's G2 line budget (target ~6,000, ceiling 6,500 — 00-overview v1.6.3).

## 4. Sources as adapters (D20)

Virlo is one adapter behind a small, shared source-adapter interface (**D14**): fetch → normalized trend items (text + media references). The config key `sources.active` (default `[virlo]`) picks which adapter(s) run during Collect; the interactive menu exposes the same choice as a picker (**D20**). **Google Trends** and **Hacker News** are named as future adapters behind the identical interface — visible in menu/config, explicitly marked not-yet-implemented, never silently hidden. Local Inspiration (**D13**) is a separate, additive influence source, not gated by `sources.active`.

**Virlo is the only MCP-backed source in the MVP.** The adapter interface is transport-agnostic — a future adapter is free to be REST, MCP, or anything else; "source adapter" does not imply "must use MCP."

**The adapter contract is small (v1.6.1).** An adapter returns normalized trend items — title, text, media references where it has any, and a **`strength` score in 0–1** it computes for its own items (`10-pipeline.md` FR-5). Items without images carry the item-level `text_only` flag and inherit the existing handling; the separate declared media-richness level and text-grounded analysis mode were withdrawn (D28 tombstone below).

- **FR-121**: The engine SHALL select active trend source(s) via the `sources.active` config key/menu picker, and SHALL list not-yet-implemented future adapters visibly rather than omitting them.
- **FR-168 / FR-169 — removed (v1.6.1, operator decision):** the declared media-richness contract and text-grounded mode are withdrawn with D28; a future text-only adapter marks its items `text_only` and inherits the existing item-level handling (`10-pipeline.md` FR-6/FR-90/FR-18). The adapter contract's one cross-source obligation is the `strength` value in 0–1 (`10-pipeline.md` FR-5).

## 5. Notion via MCP

Notion supplies optional brand context, gated by `notion_influence` (**D7**: off | copy | full).

**Self-hosted, token-based, stdio only.** The engine uses Notion's self-hosted, token-based MCP server, launched as a local stdio subprocess (Section 2) and authenticated by `NOTION_TOKEN` (an integration secret from Notion's developer settings), delivered via the per-server env dict. *Known risk (2026-08-09):* the `makenotion/notion-mcp-server` repo carries an explicit maintenance warning ("we may sunset this local MCP server repository in the future; issues are not actively monitored"). FR-113's version pinning is the mitigation; if the package is ever pulled, the pinned version keeps working. *Named fallback (also 2026-08-09):* Notion's **hosted** MCP (`mcp.notion.com/mcp`, streamable HTTP) now documents **headless auth via a personal access token sent as a custom `Authorization: Bearer` header** — so the original disqualifier ("interactive browser login only") no longer holds for the PAT mode. If the local server sunsets, the swap is a config-level change to an HTTP-transport entry with `auth_env: NOTION_TOKEN`; the interactive OAuth flow remains out of scope either way. Notion's **hosted OAuth endpoint** (`mcp.notion.com`) is explicitly **out of scope** — it requires an interactive browser login, incompatible with an unattended, scheduled run (Windows Task Scheduler, **D8**).

**Setup prerequisite, not a runtime failure.** Each page/database listed in config must be **shared with the integration once**, in Notion's UI, before it can ever be fetched — a one-time setup step documented in First-Run Setup (`30-configuration-and-run.md`), distinct from a page that *was* shared and later becomes unreadable at runtime (deleted, unshared, ID typo — see Section 10).

**Configuration & fetch timing.** Page/database IDs are grouped by context type (brand voice, offers, ICP, topics), each independently optional. All configured content is fetched once at run start during Collect and cached in memory for the whole run, so every creative in a batch sees the same brand snapshot.

**No condensation pass.** Earlier drafts summarized long fetched content through an extra Luna call before use (FR-37). That pass is **removed** — the brand-context block is built by concatenating voice/offers/ICP/topics and **truncated to a fixed character budget** (configurable, per context type) if it exceeds it. A plain cut, not a model call: cheaper, deterministic, no LLM dependency in a stage that should be fast.

**Injection**, per D7: `copy` → Write stage only; `full` → also Generate stage; `off` → Notion never fetched, no session opened.

- **FR-34**: The engine SHALL only open a Notion MCP session and fetch configured pages when `notion_influence` is `copy` or `full`.
- **FR-35**: Notion page/database IDs SHALL be configurable per context type (brand voice, offers, ICP, topics), with any unset type simply omitted from the brand-context block.
- **FR-36**: The engine SHALL fetch all configured Notion content exactly once per run, at run start, and cache it in memory for reuse by every creative in the batch.
- **FR-37** — removed (Luna condensation pass deleted; superseded by fixed character-budget truncation, FR-124).
- **FR-122**: The engine SHALL connect to Notion via the self-hosted, token-based stdio MCP server (`NOTION_TOKEN`) as the shipped default; the hosted endpoint's **interactive OAuth flow** SHALL NOT be used. ## 7. OpenRouter REST

OpenRouter is the routing layer for both LLM roles: **Sonnet 5** (visual trend analysis in Analyze, and the optional vision check) and **GPT 5.6 Luna** (copywriting in Write). Both are called through OpenRouter's chat-completions-style REST endpoint over `httpx` — no SDK, no MCP.

**Vision inputs — base64 only.** Every vision-bearing call sends already-downloaded local image bytes as base64 content parts; there is no CDN-URL fallback path. This removes a slow or dead external link as a point of failure for an in-flight paid LLM call. This is an OpenRouter-vision-only concern: RENDER reference images sent to Kie.ai (Section 8) are always passed as public URLs (Virlo CDN or Kie-hosted), never base64.

**Reasoning.** GPT 5.6 Luna is a reasoning model — reasoning tokens are billed and reported alongside output tokens. Reasoning effort is configured per role, defaulting to low/off for the copywriting role to keep cost predictable, and reasoning-token spend is included in cost accounting alongside prompt/completion tokens.

**Structured output, strict.** Style-brief (Analyze) and copy (Write) outputs are requested using the strictest structured-output/schema mode the selected model's provider routing supports, with routing configured to only route to providers that actually honor it — not a loose "ask nicely for JSON" convention. Both default models advertise structured-output support on OpenRouter (verified 2026-08-09); whether strict schema mode composes cleanly with Luna's *reasoning* output in practice is a one-call day-one check (OQ-22, `00-overview.md`) — the tolerant-parse fallback below is the safety net either way.

**Tolerant parse before retry.** A response that fails strict parsing is not immediately failed: the engine first attempts a tolerant local parse — extract the first balanced JSON object, strip markdown code fences — before spending the one allowed retry. Only if the tolerant parse also fails does the retry count against the FR-41 cap.

**Truncation handled distinctly.** A response cut short by hitting the token limit (detected via the API's finish/stop reason) is retried once with either a higher max-token limit or a shorter-content request — never an identical retry, which would just truncate again.

**Token limits.** Per-call max-token limits (and temperature/other sampling params) are set from config per model role, with a configured **floor** — a minimum below which the value cannot be set — so a misconfigured tiny limit cannot silently truncate every call.

**Vision downscaling.** For ANALYSIS calls, reference images are downscaled to ~1024px on the long edge / JPEG, capped at ~6 images per call; full-resolution originals are kept untouched for RENDER references passed to Kie.ai.

**Out of credits is a run condition, not a call condition.** OpenRouter answers an exhausted balance with **HTTP 402**. Like Kie's 402 (Section 8, FR-167), no retry can fix it and every subsequent LLM call will fail identically — so it is recognized once and handled at run scope: remaining LLM-dependent work (analysis calls, copy calls, vision checks) is **skipped with the explicit reason "OpenRouter credits exhausted"** rather than each call burning its retry budget on a certainty. The run does not abort: whatever creatives already have copy and already have renders are packaged normally, and the shortfall is stated plainly in the run summary. The two 402 conditions are reported separately — "top up Kie credits" and "top up OpenRouter credits" are different actions for the operator.

**Retries.** OpenRouter 429/5xx retries use `http_max_attempts` (default **3**) with exponential backoff. The structured-parse retry (FR-41) is a separate, harder cap of exactly **1**.

**Reproducibility.** Analysis and copy calls use a stable, configured temperature and a fixed system prompt per role, so the same trend through the same config produces comparable style briefs — useful for `both`-mode A/B comparison and debugging.

- **FR-39**: The engine SHALL call OpenRouter directly via REST for all Sonnet 5 and GPT 5.6 Luna calls.
- **FR-40**: Vision-bearing OpenRouter calls SHALL send reference images as base64-encoded content parts drawn from already-downloaded local image bytes — never by re-fetching the CDN URL at call time.
- **FR-41**: Structured OpenRouter responses SHALL be requested in strict schema/structured-output mode; a response that fails both strict and tolerant parsing (FR-126) SHALL trigger exactly one retry before the call is treated as failed for that creative.
- **FR-125**: OpenRouter provider routing for structured-output calls SHALL be configured to route only to providers that honor the requested schema mode.
- **FR-126**: On a malformed response, the engine SHALL attempt a tolerant local parse (first balanced JSON object, fences stripped) before counting the FR-41 retry.
- **FR-127**: A response truncated per its finish/stop reason SHALL be retried with a higher token limit or a shorter-content request, never an identical retry.
- **FR-128**: Reference images for ANALYSIS calls SHALL be downscaled to ~1024px long edge / JPEG, capped at ~6 images per call; RENDER references SHALL remain full-resolution.
- **FR-129**: Analysis and copy calls SHALL use a stable, configured temperature and a fixed per-role system prompt.
- **FR-248**: An OpenRouter HTTP 402 (credits exhausted) SHALL be treated as a whole-run condition — not retried, recognized once — after which all remaining LLM-dependent work SHALL be skipped with the reason "OpenRouter credits exhausted"; the run SHALL still package everything already produced, and SHALL report the OpenRouter shortfall distinctly from a Kie 402 (FR-167).
- **NFR-12**: Per-call token limits for each OpenRouter model role SHALL be configurable, not hardcoded.
- **NFR-111**: Per-role token limits SHALL carry a configured floor.

## 8. Kie.ai REST

Kie.ai is the image/video generation backend, called directly via REST over `httpx` using its async job model.

**Confirmed job contract.** Every Kie.ai generation — image, carousel slide, or reel — goes through the same two calls: `POST /api/v1/jobs/createTask` with a body of `{model, input, callBackUrl?}` (`model` is the Kie model id, `input` is the model-specific parameter object; Bearer auth, confirmed), and `GET /api/v1/jobs/recordInfo?taskId=<id>` to poll it. `recordInfo` returns a `state` of **`waiting`, `queuing`, `generating`, `success`, or `fail`** (five states, verified 2026-08-09 — not three): the engine treats every non-terminal state (`waiting`/`queuing`/`generating`) identically as *pending*, and classification code never branches on which pending state it is. On success, `resultJson.resultUrls` holds the public URL(s) of the generated asset(s); on failure, `failCode`/`failMsg` explain why; `costTime` reports render duration for logging. Kie's default account rate limit is ~20 new `createTask` requests per 10 seconds — a wave of ~14 jobs fits in one burst, but `max_inflight_render_jobs` should stay at or under that ceiling.

**No dedicated batch endpoint.** Kie.ai has no separate "submit N jobs at once" call. "Batch submission" (per **D5**, FR-42) means the engine fires concurrent `createTask` calls, one per job, then polls all of them together with `recordInfo` — the async, gather-everything behavior is unchanged; only FR-42's wording is corrected to match the real API shape.

**`callBackUrl` is unused, deliberately.** `createTask` accepts an optional `callBackUrl` for a completion push notification, but a local workstation run has no public endpoint to receive it — so the engine never sets it and polling `recordInfo` remains the only completion signal.

**Models used:**
- **GPT Image 2** — generates images and carousel slides, including reel seed frames. **Route split (OQ-17 resolved 2026-08-09):** Kie's `gpt-image-2-text-to-image` route accepts **no image inputs at all**; its sibling route **`gpt-image-2-image-to-image`** accepts **`input_urls` — an array of up to 16 image URLs**. The `gpt-image-2` profile therefore submits every **reference-bearing** job (the overwhelming default, per D2/FR-18) to `gpt-image-2-image-to-image`, and only **reference-free** jobs (`text_only` trends, moderation fallback, failed uploads) to `gpt-image-2-text-to-image`. Full input surface in Section 8c. Resolution (1K/2K/4K) and aspect ratio per platform/format come from config.
- **Seedance 2.5** (Kie model id `bytedance/seedance-2-5`) — generates reels. Text-to-video and image-to-video (optional seed frame, **D10**), with native AI audio (**D22**) and viral-video motion references (**D23**). 9:16 vertical, short duration. Per-unit price is still unpublished by Kie, so reel planning stays blocked until `price_per_unit.reel_second` is set in config (Section 11).

**Async, concurrent, per-job isolation.** Per **D5**, once a batch is submitted the engine polls all jobs concurrently (`asyncio.gather`), never serially. The poll interval is `poll_interval_s` (default **3**, canonical in `30-configuration-and-run.md`); per-job timeouts are `image_job_timeout_s` (180) and `video_job_timeout_s` (300, canonical in `30-…`). Three seconds is the deliberate middle: fast enough that a 20-second image isn't sitting finished and unnoticed, slow enough that a five-minute reel window doesn't cost hundreds of status calls. After a job's first 60 seconds of pending, its own poll interval widens to ~10 s — reels spend most of their life in that regime; images are unaffected.

**A failed poll is never a failed job.** `http_max_attempts` governs `createTask` and file-upload calls **only**. A `recordInfo` poll that errors (network drop, 5xx, timeout) is simply retried at the next poll tick — with backoff on 429/5xx — indefinitely, bounded solely by the job's own timeout and `run_deadline_min`. The alternative reading (three failed polls = failed job) would let a 30-second router reboot mark every concurrently-polling paid job failed at once while the results sit finished at Kie; that reading is explicitly wrong.

**A timed-out render job is never resubmitted.** A job that hits its per-job timeout is treated as failed for the plan (FR-44) but is **not** retried: it was paid for at submission, may still complete unclaimed at Kie, and its `taskId` is in the ledger (`10-…` FR-203). The only sanctioned resubmissions remain the moderation-refusal fallback (`10-…` FR-97) and the vision-check re-render (`10-…` FR-105), each capped at one.

**Polling measures elapsed time with a monotonic clock**, never wall-clock time. A workstation run is exactly the environment where the machine sleeps, hibernates, resumes, or has its clock corrected mid-run; a wall-clock timeout would declare a healthy job "stuck" purely because the laptop lid was shut. Elapsed-time accounting for both the per-job timeout and `run_deadline_min` uses the monotonic source.

**Three job outcomes, not two.** A stuck/failed job fails only that job — logged and skipped — never the batch. But "failed" is not only `state: fail`:

1. **Fail** — `recordInfo` returns `state: fail` with `failCode`/`failMsg`. Classified (moderation/policy vs transient) per Section 10.
2. **Stuck** — no terminal state within the per-job timeout. Logged with the job id and the timeout value exceeded.
3. **Success with an unusable result** — `state: success`, but `resultJson.resultUrls` is **empty, missing, malformed, or points at a URL that cannot be downloaded** (404, dead host, zero-byte body, non-image/video content). This is treated **identically to a failed job**: the creative is skipped, the spend is still counted (it was submitted — see the budget rules in `10-pipeline.md`), and the log line names the sub-cause (`empty_result_urls` / `result_url_unreachable`) rather than laundering it into a success. A green status code with nothing behind it is the most dangerous failure shape precisely because it looks fine — naming it is the point.

**Error codes worth naming.** Two failure shapes get distinct handling rather than falling into a generic "job failed" bucket: HTTP 402 (insufficient Kie balance) is a whole-run condition, not a single-job one — a retry cannot fix it, so the run reports "top up Kie credits" and skips all remaining render submissions; HTTP 429 (rate limit) gets the same bounded backoff as every other integration — `http_max_attempts`, default 3 (Section 2, NFR-14).

**No generation seed.** Kie.ai's `recordInfo` response exposes no generation seed or job parameters for either model — renders are not reproducible from the API alone (this closes the earlier open question). Every asset's meta file states this plainly rather than promising reproducibility.

- **FR-42**: The engine SHALL submit image and video generation jobs to Kie.ai using its async job model — concurrent `createTask` calls, since Kie.ai has no dedicated batch endpoint — polled together via `recordInfo`.
- **FR-43**: The engine SHALL poll all in-flight Kie.ai jobs concurrently; poll interval (`poll_interval_s`, default 3) and per-job timeout SHALL be configurable.
- **FR-44**: A Kie.ai job that times out or returns a failed status SHALL fail only that job's creative, logged and skipped, without aborting or delaying the rest of the batch.
- **FR-242**: A Kie.ai job reporting `state: success` whose `resultJson.resultUrls` is empty, missing, malformed, or not downloadable SHALL be treated identically to a failed job — creative skipped, spend counted, logged with the distinguishing sub-cause — and SHALL NOT be recorded as a successful render.
- **FR-243**: Kie.ai poll scheduling and all job/run timeout accounting SHALL use a monotonic clock, so host sleep, hibernation, resume, or wall-clock adjustment cannot cause a healthy job to be declared stuck.
- **FR-167**: A Kie.ai HTTP 402 (insufficient balance) response SHALL be treated as a whole-run condition — reported as "top up Kie credits" — and SHALL skip all remaining render submissions rather than retrying.
- **NFR-13**: Image resolution/aspect ratio (GPT Image 2) and resolution/duration (Seedance 2.5) SHALL be configurable per platform/format combination.

### 8b. Kie file-upload API — the engine's one path from local bytes to a public URL (D23)

Kie's renderers accept **URLs, never file bytes**. Two different needs therefore run through the same door: the trend's winning post video (below), and any **locally sourced reference image** — the Inspiration folders (D13, including a niche config's own, D27) and a campaign brief's own images (D26). Both are uploaded via Kie's file-upload API to obtain a public URL before attachment. It is one upload path, not two subsystems.

**OQ-5 is closed (2026-08-09).** The file-upload API exists and is documented: `POST https://kieai.redpandaai.co/api/file-stream-upload` (multipart binary, for large files; params `file`, `uploadPath`, optional `fileName`), plus an upload-from-URL endpoint and a base64 variant (<10 MB). Note the host is `kieai.redpandaai.co`, **not** `api.kie.ai`. Docs state support for "images, videos, documents, and more"; mp4/mov are safe, **mkv remains a one-line spot-check at build**. **New hard constraint the design must respect: uploads are temporary — Kie's quickstart states auto-deletion after 24 hours (one doc page says 3 days; the engine treats every upload URL as same-run-only and never relies on the longer figure). Generated *outputs* are retained ~14 days.** Harmless for the same-run render chain (minutes, not days), but an upload URL can never be reused by a later run, a re-render, or a Phase 2 publish — anything touching Kie-hosted uploads later must re-upload (tracked with OQ-20 in `00-overview.md`).

**Local reference images.** Each local image is uploaded independently, before the render job is submitted, and the returned URL is what appears in the job's reference list (`reference_image_urls` for Seedance; the equivalent image-input channel for GPT Image 2, Section 8c). A **per-image upload failure removes that image only** — the job proceeds with the remaining references, exactly as a dead CDN URL does under FR-247, and the failure is logged with the local filename and the upload error. A job whose local references *all* fail to upload still runs on whatever trend references it has.

**Video motion reference.** To give Seedance 2.5 a real motion reference instead of a still frame, the engine fetches the trend's own winning post video and hands it to Kie as a `reference_video_urls` entry:

1. **Probe first, download second.** `yt-dlp` (a declared project dependency, not an assumed system tool) is invoked in a **metadata-only mode** — no media bytes fetched — to read the video's duration. yt-dlp supports this natively; ffmpeg is never invoked, because ffmpeg is not part of this engine.
2. **Qualify before spending bandwidth.** A video that fails the duration bound is **never downloaded at all**. Only a video that passes the probe proceeds to a full download. Anything longer is skipped, not truncated — trimming would need ffmpeg.
3. **The bound is ≤28 s (OQ-6 closed 2026-08-09).** Kie's `bytedance/seedance-2-5` route documents the **full tier**: `reference_video_urls` max 10 videos, mp4/mov, 2–30 s each, **total reference-video duration ≤30 s**, <200 MB each; `reference_image_urls` max **30** images (<30 MB each). The qualifying bound is therefore the config key `reel_reference_max_s`, default **28** — safely inside the 30 s ceiling (canonical in `30-configuration-and-run.md`). The earlier conservative 13 s default is retired; the engine's practical reference-image attachment (≤3 per FR-91 plus the seed frame) sits far under the documented 30.
4. **Upload.** The qualifying file is uploaded via Kie's file-upload API to obtain a public URL Seedance can reference (endpoints confirmed above; 3-day expiry is irrelevant to a same-run reference).
5. **Reference.** The returned public URL goes into `reference_video_urls`, cited in the prompt via Seedance's `@Image`/reference syntax alongside any image references.

**Working files are cleaned up; output files never are.** Downloaded videos live in a run working directory, not in `output/`. At end of run — success, failure, or abort — every working file that was **disqualified, failed to upload, or has already been uploaded** is deleted. `40-outputs-and-logging.md`'s no-delete rule (FR-86) protects the *output folder*; it says nothing about scratch space, and an engine that leaves a growing pile of downloaded videos on a workstation is a defect. Cleanup failure (file locked, permission denied) is logged as a warning and never fails the run.

**Failure anywhere degrades, never blocks.** A failure at any step — probe fails, download blocked or fails, no candidate video within the duration bound, upload fails — degrades that reel to seed-frame-only generation (the D18 seed-frame image plus whatever reference images are already in play), logged with the specific step that failed. It never fails the whole creative or the batch.

**Risk note.** Downloading a third-party platform's video via yt-dlp sits in a platform-ToS gray zone; this is a known, accepted operator risk for local, non-redistributed use as a model input, not a legal endorsement.

- **FR-160**: The engine SHALL determine a candidate video's duration via a **metadata-only `yt-dlp` probe performed before any media download** (never ffmpeg); a video that fails the duration bound SHALL NOT be downloaded.
- **FR-161**: The qualifying duration bound SHALL be the config key `reel_reference_max_s`, default **28 seconds** (OQ-6 closed: Kie serves the full tier, total reference video ≤30 s); longer videos SHALL be skipped, never trimmed. The bound is also a **price lever** (v1.6.6): Kie bills a qualifying reference's seconds at the full with-video rate, so the worst-case reel price scales with this key (break-even `input < 0.65 × output`; spikes/RESULTS.md §C).
- **FR-162**: A qualifying downloaded video SHALL be uploaded via Kie's file-upload API to obtain the public URL passed into `reference_video_urls`.
- **FR-163**: A failure at any step of the probe/download/qualify/upload chain SHALL degrade that reel to seed-frame-only generation, logged with the failing step, and SHALL NOT fail the batch.
- **FR-244**: Locally sourced reference images (Inspiration folder, brief-supplied references, niche pools) SHALL be uploaded via the same Kie file-upload API used for video references to obtain public URLs before attachment to any render job; a per-image upload failure SHALL remove only that image, be logged with filename and error, and SHALL NOT prevent the job from proceeding with its remaining references.
- **FR-249**: Working-directory files downloaded or produced during a run — disqualified videos, uploaded videos, failed-upload artifacts — SHALL be deleted at end of run on every exit path; the `output/` folder SHALL remain untouched by this cleanup (FR-86), and a cleanup failure SHALL be logged as a warning without failing the run.
- **NFR-160**: `yt-dlp` SHALL be a declared, pinned project dependency, not an assumed system tool — **pinned but routinely bumped**: platform extractors break regularly (TikTok repeatedly through 2025–2026; Instagram commonly needs a cookies strategy), and yt-dlp's own remedy for breakage is "update". A broken extractor is already a handled degrade (FR-163); the bump policy exists so degradation is temporary, not permanent.

### 8c. GPT Image 2 input surface

Seedance's input object is enumerated field by field in Section 8a. GPT Image 2's was not — and it is the **more** load-bearing of the two, because every single image, every carousel slide, and every reel seed frame goes through it. This section closes that gap.

**The one assumption the whole product rests on — resolved (OQ-17 closed 2026-08-09).** D2 and `10-pipeline.md` FR-18 both state that the actual winning Virlo images are attached as **image inputs** to every GPT Image 2 job, in both `analyzed` and `direct` mode. That is the visual-fidelity backbone. Secrets are supplied via environment variables, loadable from a local `.env` file, never committed and never hardcoded:

| Variable | Used by | Missing-key behavior |
|---|---|---|
| `VIRLO_API_KEY` | Virlo MCP wrapper (Section 3), REST calls to `api.virlo.ai` | Run aborts at pre-flight — no trend data means no run is possible. |
| `NOTION_TOKEN` | Integration secret for the self-hosted, token-based Notion MCP server (stdio, Section 5) | `notion_influence` is forced to `off` for the run with a clearly logged warning; run proceeds without brand context. |
| `POSTIZ_API_KEY` | Postiz's public API key (Settings → Developers → Public API on the operator's instance); used by the Phase 2 REST publisher (Section 6) for `Authorization: <key>` and, optionally, by Postiz's MCP ops seam | N/A in MVP; Phase 2 `--publish` refuses to run without it. Not required for MVP generation runs at all. |
| `POSTIZ_BASE_URL` | Base URL for the Phase 2 Postiz REST publisher; defaults to `https://api.postiz.com/public/v1` (hosted cloud, 60-publishing FR-225); a self-hosted URL works too | N/A in MVP; Phase 2 uses the default when unset — never a refusal. Not a secret in the credential sense, but env-sourced alongside the key. |
| `OPENROUTER_API_KEY` | OpenRouter REST (Sonnet 5, GPT 5.6 Luna) | Run aborts at pre-flight — no analysis or copy is possible without it. |
| `KIE_API_KEY` | Kie.ai REST (GPT Image 2, Seedance 2.5) | Run aborts at pre-flight — nothing can be generated without it. |

A missing key degrades only the features that need it, loudly and early, never silently. Keys structurally required for any output (Virlo, OpenRouter, Kie.ai) cause a pre-flight abort. Keys gating an optional feature (Notion, Postiz) degrade or refuse that feature only.

**Secrets hygiene is absolute (D30).** Every key in the table above lives only in `.env` or real environment variables — never committed, never hardcoded. Crucially, a key is **never interpolated into any LLM prompt or template** and **never sent to any model**: the prompt-template layer (`prompts/`, `briefs/`, `10-pipeline.md`) has no placeholder that could resolve to a secret value, so a key cannot leak through the Analyze/Write generation path even by accident. Keys flow into exactly two places: an HTTP `Authorization`/API-key header for REST calls (OpenRouter, Kie.ai, Postiz), or a per-server MCP environment dict for stdio servers (Section 2). Because run.log and events.jsonl log full request payloads and prompts for debuggability, redaction is the deliberate backstop, not the primary defense — every logged payload is scrubbed of Authorization headers and key-shaped values at the logging boundary before it is written, per `40-outputs-and-logging.md`'s FR-152.

- **FR-45**: The engine SHALL validate required secrets at pre-flight, before any MCP session is opened or any paid API call is made.
- **FR-46**: Missing `VIRLO_API_KEY`, `OPENROUTER_API_KEY`, or `KIE_API_KEY` SHALL abort the run at pre-flight with a clear, specific error identifying the missing key.
- **FR-47**: Missing `NOTION_TOKEN` SHALL force `notion_influence` to `off` for the run and SHALL log a clear warning, without aborting the run.
- **NFR-112**: No API key SHALL ever be interpolated into an LLM prompt/template or sent to any model; every key SHALL flow only into HTTP auth headers or per-server MCP environment dicts, with logged payloads redacted at the logging boundary per `40-outputs-and-logging.md` FR-152.

## 10. Failure modes per integration (transport-level)

Per the shared philosophy: **degrade and report, never block the whole run.** This file owns **transport-level** failure behavior only — what happens at the MCP/REST/network boundary. Plan-level consequences (which creative gets skipped, how a batch degrades, which trend gets dropped) are owned by `10-pipeline.md` §10; output-only cases (disk, gallery, interrupted-run packaging) are owned by `40-outputs-and-logging.md`. Rows are not duplicated across files — cross-reference instead.

| Failure | Scope | Behavior |
|---|---|---|
| MCP server won't start (stdio subprocess fails to launch) | That integration's session | Logged as a startup failure; per-integration consequence (abort vs. degrade) owned by `10-pipeline.md`. |
| MCP startup timeout (server too slow to become usable) | Same as above | Distinct from a launch failure and from a per-tool-call timeout (Section 2); logged with the configured startup-timeout value exceeded. |
| MCP tool call error (server returns an error response) | The single call | Logged with tool name and error; caller treats it as "no data" for that call. |
| MCP call timeout (single tool call) | The single call | Same as a tool call error — logged, treated as no data, no indefinite hang. |
| Virlo wrapper auth error (401/403 → MCP auth error) | That call, likely all subsequent Virlo calls this run | Not retried (a retry cannot fix bad credentials); logged clearly naming `VIRLO_API_KEY` as the likely cause. |
| Virlo wrapper rate-limit (429 → MCP rate-limit error) | That call | Bounded retry with backoff — `http_max_attempts`, default 3 (Section 3); persistent limiting surfaces as repeated no-data. |
| Virlo fails partway through Collect (some monitor ids succeed, later ones error/time out) | Per monitor id | **Per-monitor degrade, never all-or-nothing.** Monitors that answered keep their data; each failing monitor is logged by id with its error class. Collect proceeds to Select with whatever responded. Whether the surviving trend pool is enough to fill the plan is owned by `10-pipeline.md`. |
| Single reference image fails to download (dead CDN URL, 404, timeout on one image) | That one image | Removed from the pool for that trend, logged with URL and reason; the job proceeds with fewer references, **including below `reference_images_per_job`** (FR-247). Only a trend left with zero usable images engages `text_only` handling in `10-pipeline.md`. |
| Kie file-upload failure for a **local** reference image (Inspiration / brief / niche pool) | That one image | Same degrade as above — image dropped, logged with filename and upload error, job proceeds with remaining references (FR-244). |
| OpenRouter 429 / 5xx | The single call | Bounded retry with exponential backoff — `http_max_attempts`, default 3. |
| OpenRouter HTTP 402 (credits exhausted) | Whole run's remaining LLM calls | Recognized once as a run-level condition, **not retried** — every subsequent LLM call would fail identically. Remaining LLM-dependent creatives are skipped with the reason "OpenRouter credits exhausted"; the run packages everything already produced. Reported distinctly from a Kie 402 — Section 7, FR-248. |
| OpenRouter malformed/truncated response | The single call | Tolerant parse attempted first; truncation retried with a higher limit or shorter input; only then does the FR-41 retry cap apply. |
| Notion token expires or is revoked **mid-run** (401/403 on a call, after pre-flight passed) | Each affected Notion call | Distinct from the pre-flight missing-key case (FR-47). Each call returns no data as usual, **but the auth failure is surfaced once as a single clear warning** naming `NOTION_TOKEN` and the fact that brand context is now missing for the rest of the run — not as a silent stream of per-page "no data" lines. One loud warning, not quiet degradation repeated *n* times. |
| Kie.ai job returns a failed status, incl. moderation/policy-class refusal | That one job | Moderation/policy-class failures are detected distinctly from generic transient failures (different status/error shape); the pipeline's fallback (resubmit once without reference images) is owned by `10-pipeline.md` — this file's role is correct classification, not handling. |
| Kie.ai job stuck (never reaches terminal status within timeout) | That one job | Logged with job id and the timeout value exceeded; treated as failed for the plan and **never resubmitted** (Section 8 — it was billed at submission and its `taskId` is in the ledger). Elapsed time is measured monotonically (FR-243), so host sleep/resume cannot fake this. |
| `recordInfo` poll call fails (network drop, 5xx, timeout on the poll itself) | That one poll attempt only | **Never terminal for the job.** The poll is retried at the next tick with backoff; only the job's own timeout or the run deadline can end a pending job (Section 8). | Kie.ai job **succeeds with an unusable result** (`state: success` but `resultJson.resultUrls` empty, missing, malformed, or not downloadable) | That one job | Treated **identically to a failed job** — creative skipped, spend still counted, logged with sub-cause `empty_result_urls` or `result_url_unreachable`. | Reel **seed frame fails to render** (Kie job fail / stuck / FR-242 unusable success) | That reel's overlay text | Detected as an ordinary Kie job outcome and logged as `seed_frame_render_failed`. The consequence — fallback to `in_model` overlay text — is owned by `10-pipeline.md` FR-24. |
| Reel seed frame **rendered, but its hosted URL is unreachable at Seedance submission** (link expired, host error, non-downloadable body) | That reel's overlay text | A separate detection from the row above, logged as `seed_frame_url_unreachable` with the URL — the render succeeded and was paid for; the handoff is what broke. | Kie.ai HTTP 402 (insufficient balance) | Whole run's remaining Kie.ai submissions | Reported plainly ("top up Kie credits"); the run skips all remaining render submissions rather than retrying — Section 8, FR-167. |
| Kie.ai HTTP 429 (rate limit) | The single call | Bounded backoff, same policy as other integrations (NFR-14). |
| yt-dlp metadata probe fails (video unavailable, blocked, network error) | That reel's video reference | Detected **before** any download, so no bandwidth is spent. Reel degrades to seed-frame-only generation, logged with the failure reason — Section 8b, FR-160/FR-163. |

- **FR-48**: Every integration failure (MCP or REST) SHALL be caught at its call site, logged with enough context to diagnose it, and SHALL degrade only the smallest affected unit of work.
- **FR-49**: No single integration failure other than a pre-flight-required secret or a total absence of trend data SHALL abort an otherwise-healthy run.
- **NFR-14**: All bounded retries SHALL have a hard maximum attempt count sourced from config — no retry path SHALL be capable of looping indefinitely. ## 12. Render-provider seam & model profiles (D34)

The model market moves faster than this codebase ever will. Two rules keep that from becoming a rewrite every quarter: **every model id is a config string**, and **every render service is reached through one small interface** rather than being wired into the pipeline by name.

**Model ids are configuration, everywhere.** Both model APIs in this file are single-endpoint services. Every OpenRouter model — the analysis model, the copy model, the vision-check model — is reached through the same chat-completions call (Section 7); every Kie model — images, carousel slides, seed frames, reels — is reached through the same `createTask` call (Section 8). Between one model and the next, the only thing that changes is the id string in the request body. So ids live in config and nowhere else (canonical keys owned by `30-configuration-and-run.md`, FR-280 block): no engine module, prompt template, log line, or cost table contains a literal model id, and none branches on one. Swapping a model for a sibling that behaves the same way — the reel model from `bytedance/seedance-2-5` to a faster or cheaper variant of the same family, or the vision/analysis role from Sonnet 5 to another OpenRouter vision model — is a **config-only change**: no code touched, no new profile written, because the sibling shares the profile it swapped into.

**The render-provider seam — exactly four operations.** All render traffic crosses one interface, and it is deliberately tiny:

1. **Submit a render job** — a model id plus the assembled inputs go out; a job handle comes back.
2. **Poll a job's status** — waiting, succeeded, or failed, with the provider's own failure reason carried through intact.
3. **Retrieve result URLs** — the public link(s) to the finished asset(s), or their honest absence.
4. **Upload a local file, receive a public URL** — the single door from local bytes to something a renderer can reference (Section 8b).

**Kie.ai is the only implementation built** — `createTask`, `recordInfo`, and the file-upload API, exactly as Sections 8 through 8c specify. Everything above the seam (Generate, the seed-frame chain, the carousel anchor chain, budget accounting, packaging) speaks only these four operations. Kie's field names, its `resultJson` shape, its state vocabulary, and its HTTP status codes stay *behind* the seam; the three-outcome classification — fail, stuck, success-with-unusable-result (FR-242) — is something the seam reports, not something each caller re-derives from raw provider JSON. A second provider is therefore an additional implementation of four operations, never a fork of the pipeline.

**Model profiles.** An id alone doesn't tell the engine how to talk to a model — providers disagree about what to call a prompt, a reference, a ratio, or a duration, and about how many references they will accept. So each render model the engine supports carries a small **profile** declaring three things:

- **Parameter mapping** — what this model calls each of the engine's standard render inputs: prompt text, reference images, aspect ratio, resolution, duration, audio. The engine assembles one standard input set; the profile renames it for the provider.
- **Reference limits** — how many reference images and videos the model accepts, plus any per-file or total size/duration ceilings, so the engine caps at the model's real limit instead of learning it from a rejected job.
- **Which prompt template set it uses** — the family of prompt scaffolds the model is written for. Template sets themselves are owned by `50-promptcraft.md`; the profile only names the one it uses.

Two profiles ship: **`gpt-image-2`** (input surface in Section 8c) and **`seedance-2-5`** (Sections 8a and 8b). A configured model id that resolves to **no known profile** is caught at **pre-flight**, never at render time: the run refuses to start, naming the offending config key, the model id found, and the profile that would have to be added — and exits with the pre-flight-refusal exit code **2** (`30-configuration-and-run.md`). There is no silent fallback to another model's parameter names and no half-spent batch discovering the gap on job three.

**Adding a new model family — the one-page recipe.** Bringing in a Kling, a Veo, or the next thing entirely is additive work, not an engine rewrite:

1. **Check the provider.** If the family is served by a provider the seam already speaks to (today: Kie), skip to step 2. If not, write one more implementation of the four operations above — that is the whole provider-side task.
2. **Write the profile.** Name the family's parameters for the standard inputs, its reference limits, and the prompt template set it will use.
3. **Write that prompt template set** in `prompts/`, per `50-promptcraft.md`. A model family fed another family's prompt conventions is the usual reason a "simple swap" produces bad output — the templates are half the profile's value.
4. **Register its price** in `price_per_unit` so the estimator can plan it. A family with no configured price refuses to plan, exactly as reels do today while the reel unit price is unset (Section 8, OQ-2).
5. **Point the config's model key at the new id.**
6. **Prove it on one item** — a small run, compared in the gallery against the references shown alongside.

No engine module appears in that list, and that is the test: if adding a family requires editing Generate or the budget code, the seam has been violated and the fix belongs in the seam, not in the caller.

- **FR-270**: Every model identifier — OpenRouter chat model ids and Kie model routes alike — SHALL be sourced from config; no model id SHALL be hardcoded in engine code, prompt templates, logging, or cost tables, and no code path SHALL branch on a literal model id. Swapping a model for one that resolves to the same profile SHALL require a config edit only.
- **FR-271**: All render traffic SHALL pass through a single render-provider interface exposing exactly four operations — submit render job, poll job status, retrieve result URLs, and upload a local file to obtain a public URL. Kie.ai SHALL be the only implementation built; no pipeline code SHALL depend on Kie-specific request fields, response shapes, state vocabulary, or status codes directly.
- **FR-272**: Every render model SHALL have a profile declaring (a) the provider's parameter names/mapping for the engine's standard inputs (prompt, references, ratio, resolution, duration, audio), (b) its reference limits, and (c) the prompt template set it uses (`50-promptcraft.md` owns the sets). Profiles for `gpt-image-2` and `seedance-2-5` SHALL ship. A configured model id resolving to no known profile SHALL cause a pre-flight refusal naming the config key, the model id, and the missing profile, exiting with code 2 — never a runtime failure mid-batch and never a fallback to another profile's parameter names.
- **FR-273**: Adding a new model family SHALL require only a new profile, a matching prompt template set, a registered per-unit price, and a config edit (plus a new provider implementation of FR-271's four operations if the family is not on an already-supported provider) — and SHALL NOT require changes to the Generate stage, the polling loop, or budget accounting.

Until all three hold, its cost model and interactive-only auth are structurally incompatible with an unattended, pay-per-use pipeline.

## Design Decisions

- **D1 — True MCP for content services, direct REST for inference — with one evidence-based exception.** Virlo and Notion are content/data systems with structured, evolving APIs best served by a standard protocol with typed tools and a shared client, and that holds cleanly for both. OpenRouter and Kie.ai are stateless inference calls — wrapping them in MCP would add a protocol hop with no benefit. Postiz was originally slotted into the same "content service, therefore MCP" bucket by design intent alone; live research into Postiz's actual MCP tool surface (D29) showed its official server has no way to accept externally generated media, so the philosophy is kept and the implementation is amended: Postiz's publishing path runs over its public REST API, with MCP retained only as an optional ops-query seam (Section 6). This is a documented, evidence-based exception to one vendor's API shape, not a reversal of the split itself — the split still keeps the codebase small (one MCP client layer, not several bespoke integrations) while keeping the fastest, and now the *only working*, path for the calls that must carry real files.
- **D5 — Everything concurrent, batch-submitted, polled with `gather`.** The old system's 93 blocking job-status polls and serialized 5–11-call chains per image are exactly what a 19-minute, 3-image run looked like. HypeSocials submits whole batches at once and polls them together, so wall-clock time is bounded by the slowest single job. This is why FR-42/FR-43 exist as hard requirements, not just an implementation preference.
- **D7 — Notion influence is a knob, not a default.** Brand grounding was one of the old system's heaviest, most opaque subsystems (a hand-copied YAML snapshot masquerading as live data). HypeSocials defaults to `off`, fetches live via real MCP only when asked, and now truncates rather than summarizes what it fetches (Section 5) — one fewer LLM dependency, deterministic cost, same goal of keeping prompts lean.
- **D16 — Every file opens with a TL;DR.** Reviewers and future collaborators need a 30-second, jargon-free entry point before the requirement-numbered detail. This file's TL;DR states the transport split and the fail-small posture in plain terms.
- **D20 — Sources are adapters; selection is a first-class choice.** `sources.active` and the menu picker (Section 4) treat "which trend source(s) feed this run" as an explicit decision, not a hardcoded assumption, so Google Trends/Hacker News slot in later without touching engine internals.
- **D21 — Virlo's MCP wrapper ships as Python, not Node.** *(Premise updated 2026-08-09: an official Virlo MCP server now exists with headless Bearer auth — Section 3 — so the wrapper is a deliberate choice for surface minimalism and churn insulation, not a necessity.)* Shipping it as a thin Python module in the same venv (Section 3) avoids introducing a second language runtime into a project whose entire premise is leanness, keeps it inside the ~3,000-line budget, and makes the five-tool contract — plus its error translation, session-pool bound and retry behavior — an explicit, reviewable part of this PRD rather than an implicit assumption. Because we write the server ourselves, its tool names are fixed by that contract, which is why the config-driven tool-name map originally specified as FR-116 was withdrawn: a rename layer for five tools with exactly one implementation is generality with no consumer. The swap path to an official Virlo server survives intact at the level that actually matters — point `mcp_servers` at a different command.
- **D22 — Reel audio in-model, default ON.** Seedance 2.5 generates synchronized AI audio natively via a single `generate_audio` boolean (Section 8a) — no ffmpeg, no separate audio pipeline, no stitching step. Matches the project's "no ffmpeg" posture (D10) while still shipping reels with sound by default; turning it off per config ships silent clips for platform-native sound overlay instead.
- **D23 — Viral-video motion references ship in MVP.** Feeding Seedance the actual winning post's video, not just a still seed frame, is the difference between "looks similar" and "moves like the trend." The yt-dlp → qualify → Kie-upload chain (Section 8b) is a small, deterministic addition, and its every failure mode degrades to seed-frame-only rather than blocking a reel — worth the added dependency and one documented ToS gray-zone risk for the visual-fidelity payoff.
- **D28 — withdrawn (v1.6.1, operator decision).** The declared media-richness property and text-grounded mode were pre-built machinery for adapters that don't exist. A future text-only adapter marks its items `text_only` and inherits the existing item-level handling (Section 4; `10-pipeline.md` FR-148/FR-149 tombstone).
- **D29 — Postiz is the committed Phase 2 target, spec'd now from live research, not left as a design sketch.** Rather than ship a "TBD, verify at build" placeholder, Postiz's actual MCP and REST surfaces were researched and verified before this amendment — the honest transport verdict in Section 6 and the full flow in `60-publishing-postiz.md` replace speculation with a plan that is implementation-ready; only its build is sequenced after MVP.
- **D30 — Secrets hygiene is absolute.** API keys are high-value, easy-to-leak strings, and this project logs everything (full prompts, full payloads) for debuggability — a combination that demands an explicit rule. Keys never enter a prompt or template, never reach a model, and are stripped from logs as a backstop even though they should never appear there in the first place (Section 9, NFR-112). This is a project-wide constraint owned here at the integration boundary where every key is actually used, and enforced at the logging boundary owned by `40-outputs-and-logging.md` (FR-152).
- **D34 — Model ids are config strings; render providers sit behind a four-operation seam; every render model carries a profile.** The model market turns over faster than this codebase will, and the old system's lesson was that model assumptions baked into code become the thing you cannot change. Keeping ids in config costs nothing — both model APIs are single-endpoint services where the id *is* the only difference between one model and another (Section 12), so the alternative would be hardcoding for no benefit. The seam is deliberately four operations wide: submit, poll, fetch results, upload. That is the smallest surface that still hides a vendor, and it is exactly the surface Kie already presents, so it costs a thin wrapper rather than an abstraction layer — a real consideration against a ~3,000-line budget. Profiles are what keep a swap honest: an id without a parameter mapping, a reference limit, and a prompt style is a promise the engine cannot keep, which is why an unknown profile refuses at **pre-flight (exit 2)** instead of failing halfway through a paid batch — the same posture as a malformed config value. The payoff is stated as a test rather than an aspiration: adding a model family must not touch Generate, the polling loop, or budget accounting (FR-273). Higgsfield.ai was the first real trial of this seam and it earned a "not yet" (Section 12a) — the seam's value is that the answer can change later without the pipeline noticing.
- **D35 — Transcript tactics: one is a brief, two are parked behind the seam** *(premise updated 2026-08-09)*. Three techniques surfaced from the operator's transcripts and were dispositioned rather than absorbed. *Product-photo-to-ad* needs **zero new machinery** — it is a worked campaign-brief example on existing D26 mechanics (brief-supplied reference images already upload through the FR-244 path), so it ships as documentation, not code. *Extension chaining* and *audio-reference music videos* stay **named future capabilities, explicitly parked — now by choice, not impossibility**: Kie's own Seedance 2.5 route exposes both primitives today (`return_last_frame` for shot chaining, `reference_audio_urls` for audio-guided generation — Section 8a), so promoting either later is config + prompt-template work behind the D34 seam, with no new provider needed. They stay out of the MVP because they are new *creative product surface* (multi-shot narratives, music-driven edits), not because the API is missing — and shipping them well needs template craft and evaluation that would dilute the MVP.
