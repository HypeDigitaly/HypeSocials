## TL;DR — Plain English

HypeSocials talks to five outside systems, split into two clean groups.

**Content systems** — Virlo (topic and post data), Notion (brand info), and later Postiz (scheduling) — are things that *hold* content, so the engine talks to them through **MCP**, a standard way for an AI app to call another program's tools. Virlo doesn't have an official MCP server, so HypeSocials ships its own tiny one, written in plain Python, that just translates Virlo's normal web API into five MCP tools — no caching, nothing fancy. One of those five simply lists the available monitors by name and id, so setting the app up the first time doesn't depend on hunting for numbers in a dashboard. Notion has a real MCP server too, but HypeSocials uses the simple "paste a token" version, not the one that needs a browser login, because runs happen unattended overnight. Postiz, coming in the next phase, is the one exception: its official AI-connector (MCP) genuinely cannot accept the image/video files this app creates, so drafts get pushed to Postiz over its plain web API instead — MCP is only used there for small lookups, not for publishing. The full Postiz plan lives in `60-publishing-postiz.md`; this file states the honest transport facts.

**Model APIs** — OpenRouter (the AI that screens topics for brand safety, selects copy, and runs the post-render quality gate via three independent critics) and Kie.ai (the service that renders images and reels) — are just plain web calls. Reels come back with AI-generated sound built in. Model APIs don't hold state between calls, so wrapping them in MCP would add nothing but slowdown.

**Models can be swapped by editing a text file, not the engine.** Every model name — the copywriter, the image model, the reel model — lives in the config file, and both model services accept whichever model you name through the same door, so moving to a newer or cheaper model of the same kind is a one-line edit. Talking to a rendering service happens through one small doorway with exactly four jobs: send work, ask if it's done, collect the finished links, and turn a file on the operator's computer into a link. Kie.ai is the only service plugged into that doorway today. Each render model also carries a short note saying what it calls its own settings and which prompt style it likes, so adding a completely new model family later means writing that note plus a set of prompts — not rebuilding the engine. Name a model the engine has no note for and the run stops before spending a cent, saying exactly which note is missing. Higgsfield.ai was researched as a second rendering service and turned down for now: it doesn't have the reel model this app depends on, and its AI-connector insists on a human logging in — which an unattended overnight run cannot do.

**The big "check this first" question has been answered.** This whole product is built on showing the image model the actual style reference pictures and saying "make something like this." Live verification (2026-08-09) confirmed Kie really does accept reference pictures — just on a sibling route of the one this file originally named: reference-bearing jobs go to the image-to-image route (up to 16 picture links per job), and only picture-less fallback jobs use the text-only route. Everything the engine sends to the image model is written out field by field in this file, nearly all of it now marked *confirmed*; the one remaining first-day check is a single cheap render proving the model actually copies the style of the pictures it is shown.

Pictures that live on the operator's own computer (a campaign brief's own images) can't be handed to a renderer as a local file — the renderer only understands web links. So they get uploaded first through Kie's file-upload API (Section 8b), and the link that comes back is what gets attached. Style guidance comes from text prompts only (the meta-style registry), not from reference images (D46).

Every connection is built to fail small: if Virlo hiccups, that one monitor is skipped, not the whole run; if Notion is unreachable, brand context is simply left out; if an image job gets stuck, that one image is skipped and the rest keep going; if one of three reference pictures won't download, the job runs with two. A render job that reports "success" but hands back nothing usable is counted as a failure, not a win — a happy status code with an empty result is still an empty result. Temporary files the engine downloads along the way are tidied up when the run ends; the finished-output folder is the only thing that is never touched. Where source data feeds the engine at all (Virlo today; Google Trends or Hacker News someday), it's plugged in through one small, swappable "source adapter" shape, so adding a new source later doesn't mean rewriting the engine.

One more thing on secrets: none of the API keys this file describes are ever shown to an AI model or written into a log file — they only ever travel inside web-request headers or a server's private environment, and anything key-shaped is scrubbed if it ever gets near a log.

## 1. Integration philosophy

HypeSocials draws a firm line between two kinds of external dependency, per **D1**:

- **Content services** — systems that hold or accept structured content (trend intelligence, brand knowledge, scheduling): **Virlo**, **Notion**, and (Phase 2) **Postiz**. Connected through **real MCP servers** wherever the server can actually do the job. The engine is a genuine async MCP client, not a REST client pretending to speak MCP.
- **Model inference APIs** — systems that take a prompt/payload and return a generation: **OpenRouter** and **Kie.ai**. Called **direct REST** over `httpx`. There is no protocol benefit to wrapping a stateless inference call in MCP.

This split is deliberate and permanent — it is not "MCP everywhere" and not "REST everywhere," it is the right transport for the right job. **Postiz is the one documented exception inside "content services":** its official MCP server has no way to ingest externally generated media (Section 6), so the load-bearing publishing path for HypeSocials' own creatives runs over Postiz's public REST API, with MCP kept only as an optional ops-query seam. This was discovered by verifying Postiz's actual tool surface (see D1, D29) — it is a fact about one vendor's API, not a reversal of the MCP-for-content-services principle, which still holds cleanly for Virlo and Notion.

- **FR-30**: The engine SHALL implement one shared async MCP client used by all MCP-backed integrations (Virlo, Notion, and Postiz's optional ops-query seam — Section 6), configured per-server via launch command/URL and transport type.
- **FR-31**: The engine SHALL open MCP sessions for the integrations a run actually needs at the start of Collect, and close all open sessions before the run ends, regardless of run outcome.
- **NFR-10**: All integration calls (MCP tool/resource calls and REST calls alike) SHALL run concurrently wherever the pipeline stage allows it (per **D5** — see FR-42, FR-43), never serialized unless a genuine data dependency requires it.

## 2. MCP client layer (shared plumbing)

One async MCP client module, built on the official Python MCP SDK, is shared by every MCP-backed integration. It does not hardcode per-server logic beyond mapping tool calls — each server's transport, launch command, and environment come from config (full schema and a worked example live in `30-configuration-and-run.md`; HTTP-transport entries additionally carry an `auth_env` field naming the environment variable that holds that server's bearer token).

**Windows-safe launch.** Two Windows-specific traps are handled explicitly: (1) npm-installed CLI tools install as `.cmd`/`.exe` shims, not bare executables, so the launcher resolves the actual shim path or launches via `cmd /c` rather than assuming a direct exec works; (2) a subprocess tree (e.g. `npx` spawning a further Node process) is fully terminated on every exit path — success, failure, timeout, or abort — via Windows job objects or an explicit `taskkill /T` sweep. A dangling MCP subprocess after a run is a bug, not a cosmetic issue.

**Per-server environment.** Each stdio server receives an explicit, minimal environment dict — only the variables that server needs, named per server in config (the Virlo wrapper gets `VIRLO_API_KEY` and nothing else; the Notion server gets `NOTION_TOKEN` and nothing else) — not the engine's full process environment forwarded wholesale.

**Timeouts, pinning, and preflight.** MCP server startup has its own configurable timeout, `mcp_startup_timeout_s` (default **20**), separate from the per-tool-call timeout, `mcp_call_timeout_s` (default **30**) — a slow-starting server and a slow individual call are different failure signatures, logged differently. Both keys are defined canonically in `30-configuration-and-run.md`. Server packages are pinned to a specific version and pre-installed (during `run.bat` bootstrap or documented setup), never resolved fresh from a registry on every run via a bare `npx pkg@latest`. A **Node/npx pre-flight check** runs only when a configured server command actually invokes `npx` or `node` — the Virlo wrapper (pure Python) never triggers it.

**Session lifecycle.** A session opens only for integrations a run actually needs, at the start of Collect, and closes as soon as its data has been fully fetched — for Virlo and Notion, that's the end of Collect. The one exception is **Postiz** (Phase 2, `--publish` runs only), whose session opens later, at the publish step.

**Serialization and how concurrency is actually obtained.** Tool calls within a single session are serialized (one in flight at a time) unless a server is specifically documented as concurrency-safe. Concurrency across different monitors/trends/creatives therefore comes from running **several independent sessions**, never from racing calls on one session. Because a stdio session is a subprocess, "several" must be a **bounded, named number** — the per-integration session pool (Virlo's is specified in Section 3) — never one process per work item. Unbounded subprocess spawning is a defect, not a speed-up.

Tool names are **not** config-mapped. The engine's only stdio servers are ones this project ships or pins, so the tool contract is fixed at the code level; the swap path to a different server implementation is still a config edit, but it is a change of *command/URL*, not of tool names (see the FR-116 tombstone below).

- **FR-110**: Stdio MCP servers SHALL be launched with an explicit, per-server environment dict (only the variables that server needs) and with Windows-safe process resolution (`.cmd`/`.exe` shim resolution, or launch via `cmd /c`).
- **FR-111**: Subprocess trees for MCP stdio servers SHALL be fully terminated on every exit path (success, failure, timeout, abort). On Windows this SHALL use a **job object with kill-on-job-close** so that even a hard kill of the engine process (Task Manager, console X, shutdown) reaps the tree; `taskkill /T` is the fallback sweep for orderly exits only.
- **FR-112**: MCP server startup SHALL have its own configurable timeout (`mcp_startup_timeout_s`, default 20), distinct from the per-tool-call timeout (`mcp_call_timeout_s`, default 30); both SHALL be sourced from config, never hardcoded.
- **FR-113**: MCP server packages SHALL be pinned to a specific version and pre-installed; no server command SHALL resolve a package fresh from a registry at run time.
- **FR-114**: An MCP session SHALL close as soon as the data it was opened for has been fetched (end of Collect for Virlo and Notion); only the Postiz session (Phase 2, `--publish`) SHALL remain open past Collect.
- **FR-115**: Tool calls within a single MCP session SHALL be serialized unless the server is documented as concurrency-safe for parallel calls; concurrency SHALL be obtained from a bounded pool of independent sessions (FR-246), never from racing calls on one session and never from unbounded subprocess spawning.
- **FR-116** — **withdrawn (v1.4)**; tool names are fixed by the wrapper contract. The swap-path to an official Virlo server remains config-level (point `mcp_servers` at a different command).
- **FR-117**: A Node/npx presence-and-version pre-flight check SHALL run only when a configured server command invokes `npx` or `node`.

## 3. Virlo via MCP

Virlo is the topic-and-post-intelligence source and the primary raw material for verbatim copy selection (see `00-overview.md` "The Pipeline at a Glance", `10-pipeline.md` for how this data is consumed in Filter/Select/Copy/Generate). The engine talks to Virlo exclusively through MCP tool calls — never a raw HTTP call to a Virlo REST endpoint from engine code.

**MVP ships the wrapper (D21 — settles OQ-3; premise updated 2026-08-09).** Virlo now ships an **official MCP server** (`https://dev.virlo.ai/api/mcp/mcp`, server card at `virlo.ai/.well-known/mcp/server-card.json`, ~49 tools, headless `Authorization: Bearer virlo_tkn_…` — no interactive login, so the disqualifier that ruled out Notion-hosted and Higgsfield MCP does **not** apply). Shipping our own wrapper is therefore a **choice, not a necessity**, and the choice stands for three reasons: a five-tool surface is reviewable, the wrapper pins the tool contract against Virlo's API churn (Virlo removed its Orbit/Comet endpoints on 2026-08-03 with days of notice), and a first-party stdio server needs no HTTP-transport auth plumbing. The official server remains the documented swap path (point `mcp_servers.virlo` at its URL). The shipped wrapper: a thin Python MCP server, `python -m hypesocials.virlo_mcp`, built on the official Python MCP SDK, running as a local stdio subprocess **in the same Python virtual environment** as the rest of the engine — no Node toolchain for this or any other first-party server. It internally calls Virlo's REST API (`api.virlo.ai`, Bearer auth via `VIRLO_API_KEY`, delivered through the per-server env dict from Section 2). Its implementation lines count toward the project's G2 line budget — it is engine code, not an exempt dependency.

**Exactly five tools, nothing more.** No speculative extras, no server-side caching layer (every call re-hits Virlo's REST API fresh), no logic beyond field normalization (reshaping REST JSON into the documented tool-return shape — it does not derive, rank, or filter; that stays in the engine's Filter/Select stages):

| Tool | Virlo REST endpoint | Returns |
|---|---|---|
| `get_trends` | `GET /v1/trends/digest` | trend/theme name, confidence, tactics[], why_it_works, timing analysis, connecting threads (global context; this endpoint does NOT create trend items in v2.0.0; `top_exemplars[]` deleted) |
| `get_monitor_analysis` | `GET /v1/agents/{id}` | deeper "why this is working" intelligence for one monitored theme, returns themes[] with engagement data |
| `get_top_videos` | `GET /v1/agents/{id}/videos` | per post/video: post_id, url, author, caption, hooks, text_overlays, views, **description (context-only, AI summary — never rendered/quoted per FR-303)**, hashtags — **all other fields verbatim, never translated** |
| `get_top_slideshows` | `GET /v1/agents/{id}/slideshows` | per post/slideshow: post_id, url, author, caption, panel_texts[], narrative_arc, views, **description (context-only, AI summary — never rendered/quoted per FR-303)**, hashtags — **all other fields verbatim, never translated**; `panel_texts` index-aligned to `panel_count` (per §0.14a) |
| `list_monitors` | `GET /v1/agents` | the monitors available to this API key: id + human-readable name (plus whatever else the endpoint volunteers, normalized away if not id/name) |

All five endpoint paths are **verified (2026-08-09)** against Virlo's live OpenAPI spec (`api.virlo.ai/openapi.json`): `GET /v1/trends/digest`, `GET /v1/agents`, `GET /v1/agents/{id}`, `GET /v1/agents/{id}/videos`, `GET /v1/agents/{id}/slideshows` all exist as claimed, base `https://api.virlo.ai/v1`, Bearer auth confirmed. **Operational prerequisite:** the Virlo API requires a payment method and a **prepaid deposit** in the Virlo billing dashboard before any call succeeds — recorded in First-Run Setup (`30-…`) and as OQ-19 (per-call pricing unknown, so "preview is $0" claims read precisely as "zero LLM/render spend").

**FR-301 — Fetch strategy (v2.1.0): slideshows-only when `sources.include_videos: false`; `order_by=created_at desc`; pages `1..fetch_pages`; dedupe by post id; client-side `publish_date` staleness cap via `sources.max_post_age_days`; used-post drop pre-rank (FR-307); rank by views among survivors; FR-246 session pool intact.**

**FR-305 — Eligibility gates (v2.1.0): Post-fetch, before ranking, one sequential gate pass applies four filters to each row:** (1) **Staleness** — drop if `published_at` exceeds `sources.max_post_age_days`; (2) **Enrichment** — drop a slideshow with no slide images (`panel_count == 0`), or — only when `sources.vision_transcribe` is off — one with no readable text at all (no non-empty `panel_texts`, no hook). The full §0.14a “≥2 usable panel slots” deck verdict is decided at ASSIGN (FR-304), because usability is defined after the merge with vision intelligence, which runs post-Confirm; a deck vision could still rescue is never dropped at fetch; (3) **Deduplication** — drop if post_id already appears in this run's history window (`trend_history_days`); (4) **Used-post exclusion** — drop if post_id is in the burned list (previous creative in this plan's COPY stage or later). Each drop increments a funnel counter: `dropped_stale` / `dropped_unenriched` / `dropped_used` (FR-155 one-place rule — counted here, reported once in summaries). **Funnel mapping note:** the gate applies four filters above (staleness, enrichment, used-post, dedupe) while the funnel prints **three drop counters** (`dropped_stale`, `dropped_unenriched`, `dropped_used`) **plus `duplicates_dropped`** (the dedup drop from filter 3). The four-filter gate precedes ranking; the three-counter funnel reports output counts at the summary point. Survivors are ranked by views and presented to Select.

**Tool parameters for media calls (verified 2026-08-11).** The `get_top_videos` and `get_top_slideshows` endpoints accept the following parameters:
- **`limit`** — integer, maximum **100** (the server silently clamps any value larger than 100)
- **`page`** — integer, **1-indexed**, and the window it selects is `limit`-relative: at `limit=100`, `page=1` is items 1–100 and `page=2` is items 101–200
- **`order_by`** — one of **`{publish_date | views | created_at}`** (verified 2026-08-11: `order_by=engagement` returns HTTP 400). **FR-301 default: `created_at` (recency-first within the window); views ranking applies post-fetch among survivors (staleness-filtered, used-post-dropped).**
- **`sort`** — one of **`{asc | desc}`**
- **`offset` is NOT a valid request parameter and MUST NEVER BE SENT** — live testing on 2026-08-11 returned HTTP 400 with the message `{"message":["property offset should not exist"]}`. The response body echoes a *derived* `offset` value (computed from `page` and `limit`); that field is **output-only** and must never appear in a request. The response carries pagination metadata: `total` (total available items), `limit` (items per page), and the computed `offset`.

**FR-293 — Topic extraction from monitor results (v2.1.0).** After Collect, a *topic* — the unit Select ranks (`10-…` FR-5/FR-6) — is extracted from each theme returned by `get_monitor_analysis`. The engine runs `_themes(analysis_data)` over each monitor's results, which may yield **zero to N topics per monitor** (per-monitor cardinality, unspecified by Virlo; topics are normalized from the themes list). Each topic carries:

- **Stable topic key** — a slug derived from the theme name (lowercase, diacritics ASCII-folded, non-alphanumerics hyphenated), used for history matching and logging.
- **`SourcePost` list** — posts extracted from `get_top_videos` and `get_top_slideshows` for that topic's theme, **ranked by views within the recency window** (age ≤ `sources.max_post_age_days`, deduplicated, used-posts dropped). Each `SourcePost` carries: `post_id`, `url`, `author`, `published_at` (ISO 8601, Virlo post publication timestamp), `caption`, `hooks`, `text_overlays`, `panel_texts` (index-aligned to `panel_count`, position-preserving with empty slots padded), `panel_count` (number of slides, consumed at ASSIGN), `image_urls` (array of slide image URLs, consumed for gallery reference), `intelligence_status` (vision-eligibility marker, consumed), `description` (context-only AI summary, never quoted per FR-303), `language` (ISO 639-1 code from Virlo's `intelligence.language_detected`, normalised at adapter; `""` when absent), `multilingual` (boolean from Virlo's `intelligence.is_multilingual`), `views` — **all verbatim from Virlo, never translated except at translation boundary (FR-343)**. (`text_overlay_contents` if returned by Virlo folds into `text_overlays` as verbatim-eligible copy material.)
- **Per-topic strength** — computed fresh from that topic's own `SourcePost` subset: `total_views` (sum), `median_views`, `velocity` (rate of view accumulation), and `engagement` (retweets/likes composite), each **min-max normalized to 0–1 within the full run's topic pool** before weighting with hardcoded defaults (total views **0.35**, median views **0.15**, velocity **0.30**, engagement **0.20**). A topic's strength is local to its own posts, not global, so topics from the same monitor get different scores when their post sets differ.
- **Slideshow-majority flag** — is this topic majority-slideshow (image panels + panel_texts + narrative arc) or majority-video (hooks, overlay text, descriptions)?
- **History key** — **format change from v1: now `<mid>::<topic_key>`** where `<mid>` is the monitor id. Old v1 entries (keyed on monitor id alone or pre-pivot theme name) stop matching; a first post-pivot run sees an empty history window by design. Entries age out per the configured window; no pruning pass runs.
- **Metadata** — topic name, `why_it_works`, tactics, top hook texts, hashtags, intelligence label lists (from Virlo's analysis).

**Invariants:** **never fewer items than pre-window** (zero themes after applying the age/dedup/drop gates → synthesize exactly one topic from the monitor aggregate); cap `sources.virlo_topics_per_monitor` (default **9**); `-1` = kill switch (one item per monitor). When a topic's fresh slideshow posts are exhausted mid-plan (no usable slides ≥2 slots after window filtering), the entry skips with `no_fresh_post_available` (funnel-counted per FR-155) — never wraps, never repeats.

The global `get_trends` digest is fetched once per run and **never creates topics of its own** — that clause is unchanged and load-bearing (its role is to enrich cross-monitor context only). `top_exemplars[]` from the digest is **dropped entirely** — the digest was discarding five posts that had been billed for; topics now source all their posts from the monitor-specific calls, preserving the niche filter and ensuring distinct post sets across topics.

**Why `list_monitors` exists.** First-Run Setup has to tell the operator which values to put in `virlo_monitor_ids`. Without this tool, the only documented answer is "find them somewhere in the Virlo dashboard" — an instruction this PRD cannot verify and the operator cannot debug. The tool powers the `--list-monitors` CLI action (canonical in `30-configuration-and-run.md`), which opens a Virlo session, prints `id — name` for every monitor the key can see, and exits at $0. It is a setup aid, not a pipeline step: no run stage calls it.

**Terminology.** "Monitor" is HypeSocials vocabulary, not Virlo's: the config key `sources.virlo_monitor_ids` (see `30-`) names the values passed as arguments to `get_monitor_analysis` / `get_top_videos` / `get_top_slideshows`, which map onto Virlo's `/v1/agents/{id}` resource.

**Error translation.** The wrapper translates Virlo's HTTP status codes into distinguishable MCP error types — auth (401/403), rate-limit (429), not-found (404), server error (5xx) — each raised as a distinct class, so engine failure handling (Section 10) can branch by class instead of parsing error text.

**Session and concurrency model.** The wrapper wraps a **stateless REST API** — it holds no cursor, no auth handshake, no per-session server state — so a session is nothing more than a live subprocess. The default is therefore **one session with serialized calls** (FR-115): cheapest, simplest, and correct for the common single-monitor run.

Collect-stage concurrency across **multiple monitor ids** is obtained by opening a **small bounded pool of wrapper sessions** — `virlo_session_pool`, a named small constant, default **3** (key registered in `30-configuration-and-run.md`) — each spawned and torn down under the existing Windows-safe launch and subprocess-tree-kill rules (FR-110, FR-111). Monitors are handed to the pool as work items; the pool never grows with the number of monitors. Three concurrent sessions is enough to hide network latency for a realistic monitor list while keeping the process count reviewable in Task Manager. **One subprocess per monitor id is explicitly forbidden.**

**Retry policy.** Retries/backoff for Virlo tool calls follow the same bounded policy used for OpenRouter and Kie.ai (Sections 7–8): `http_max_attempts` (default **3**, canonical in `30-configuration-and-run.md`) with exponential backoff, never unbounded, never retried for a class (auth, not-found) that a retry cannot fix.

## 7. OpenRouter REST

OpenRouter is the routing layer for both LLM roles: **Sonnet 5** (optional vision check on finished images) and **GPT 5.6 Luna** (copywriting in Write). Both are called through OpenRouter's chat-completions-style REST endpoint over `httpx` — no SDK, no MCP.

**Vision inputs — base64 only.** Every vision-bearing call sends already-downloaded local image bytes as base64 content parts; there is no CDN-URL fallback path. This removes a slow or dead external link as a point of failure for an in-flight paid LLM call. This is an OpenRouter-vision-only concern: RENDER reference images sent to Kie.ai (Section 8) are always passed as public URLs (Virlo CDN or Kie-hosted), never base64.

**Reasoning.** GPT 5.6 Luna is a reasoning model — reasoning tokens are billed and reported alongside output tokens. Reasoning effort is configured per role, defaulting to low/off for the copywriting role to keep cost predictable, and reasoning-token spend is included in cost accounting alongside prompt/completion tokens.

**Structured output, strict.** Copy (Write) output is requested using the strictest structured-output/schema mode the selected model's provider routing supports, with routing configured to only route to providers that actually honor it — not a loose "ask nicely for JSON" convention. The default model advertises structured-output support on OpenRouter (verified 2026-08-09); whether strict schema mode composes cleanly with Luna's *reasoning* output in practice is a one-call day-one check (OQ-22, `00-overview.md`) — the tolerant-parse fallback below is the safety net either way.

**Tolerant parse before retry.** A response that fails strict parsing is not immediately failed: the engine first attempts a tolerant local parse — extract the first balanced JSON object, strip markdown code fences — before spending the one allowed retry. Only if the tolerant parse also fails does the retry count against the FR-41 cap.

**Truncation handled distinctly.** A response cut short by hitting the token limit (detected via the API's finish/stop reason) is retried once with either a higher max-token limit or a shorter-content request — never an identical retry, which would just truncate again.

**Token limits.** Per-call max-token limits (and temperature/other sampling params) are set from config per model role, with a configured **floor** — a minimum below which the value cannot be set — so a misconfigured tiny limit cannot silently truncate every call.


**Out of credits is a run condition, not a call condition.** OpenRouter answers an exhausted balance with **HTTP 402**. Like Kie's 402 (Section 8, FR-167), no retry can fix it and every subsequent LLM call will fail identically — so it is recognized once and handled at run scope: remaining LLM-dependent work (analysis calls, copy calls, vision checks) is **skipped with the explicit reason "OpenRouter credits exhausted"** rather than each call burning its retry budget on a certainty. The run does not abort: whatever creatives already have copy and already have renders are packaged normally, and the shortfall is stated plainly in the run summary. The two 402 conditions are reported separately — "top up Kie credits" and "top up OpenRouter credits" are different actions for the operator.

**Retries.** OpenRouter 429/5xx retries use `http_max_attempts` (default **3**) with exponential backoff. The structured-parse retry (FR-41) is a separate, harder cap of exactly **1**.

**Reproducibility.** Copy calls use a stable, configured temperature and a fixed system prompt per role, so the same topic through the same config produces comparable copy selections for debugging.

- **FR-39**: The engine SHALL call OpenRouter directly via REST for all Sonnet 5 and GPT 5.6 Luna calls.
- **FR-40**: Vision-bearing OpenRouter calls SHALL send reference images as base64-encoded content parts drawn from already-downloaded local image bytes — never by re-fetching the CDN URL at call time.
- **FR-41**: Structured OpenRouter responses SHALL be requested in strict schema/structured-output mode; a response that fails both strict and tolerant parsing (FR-126) SHALL trigger exactly one retry before the call is treated as failed for that creative.
- **FR-125**: OpenRouter provider routing for structured-output calls SHALL be configured to route only to providers that honor the requested schema mode.
- **FR-126**: On a malformed response, the engine SHALL attempt a tolerant local parse (first balanced JSON object, fences stripped) before counting the FR-41 retry.
- **FR-127**: A response truncated per its finish/stop reason SHALL be retried with a higher token limit or a shorter-content request, never an identical retry.
- **FR-128 — withdrawn (v2.0.0).** Vision-check calls read native resolution, not downscaled (`10-pipeline.md` FR-105). The ~1024px downscale for *analysis* is withdrawn with the deletion of the Analyze stage; with it goes the engine's last Pillow use. (FR-27 itself SURVIVES — the vision check is the `analysis` LLM role's one remaining owner.)
- **FR-129**: Copy calls SHALL use a stable, configured temperature and a fixed per-role system prompt; vision-check calls use the configured temperature for that role (default off/low for copywriting to keep cost predictable).
- **FR-248**: An OpenRouter HTTP 402 (credits exhausted) SHALL be treated as a whole-run condition — not retried, recognized once — after which all remaining LLM-dependent work SHALL be skipped with the reason "OpenRouter credits exhausted"; the run SHALL still package everything already produced, and SHALL report the OpenRouter shortfall distinctly from a Kie 402 (FR-167).

## 8. Kie.ai REST

Kie.ai is the image/video generation backend, called directly via REST over `httpx` using its async job model.

**Confirmed job contract.** Every Kie.ai generation — image, carousel slide, or reel — goes through the same two calls: `POST /api/v1/jobs/createTask` with a body of `{model, input, callBackUrl?}` (`model` is the Kie model id, `input` is the model-specific parameter object; Bearer auth, confirmed), and `GET /api/v1/jobs/recordInfo?taskId=<id>` to poll it. `recordInfo` returns a `state` of **`waiting`, `queuing`, `generating`, `success`, or `fail`** (five states, verified 2026-08-09 — not three): the engine treats every non-terminal state (`waiting`/`queuing`/`generating`) identically as *pending*, and classification code never branches on which pending state it is. On success, `resultJson.resultUrls` holds the public URL(s) of the generated asset(s); on failure, `failCode`/`failMsg` explain why; `costTime` reports render duration for logging. Kie's default account rate limit is ~20 new `createTask` requests per 10 seconds — a wave of ~14 jobs fits in one burst, but `max_inflight_render_jobs` should stay at or under that ceiling.

**No dedicated batch endpoint.** Kie.ai has no separate "submit N jobs at once" call. "Batch submission" (per **D5**, FR-42) means the engine fires concurrent `createTask` calls, one per job, then polls all of them together with `recordInfo` — the async, gather-everything behavior is unchanged; only FR-42's wording is corrected to match the real API shape.

**`callBackUrl` is unused, deliberately.** `createTask` accepts an optional `callBackUrl` for a completion push notification, but a local workstation run has no public endpoint to receive it — so the engine never sets it and polling `recordInfo` remains the only completion signal.

**Models used:**
- **GPT Image 2** — generates images and carousel slides, including reel seed frames. **Route split (OQ-17 resolved 2026-08-09):** Kie's `gpt-image-2-text-to-image` route accepts **no image inputs at all**; its sibling route **`gpt-image-2-image-to-image`** accepts **`input_urls` — an array of up to 16 image URLs**. The `gpt-image-2` profile therefore submits every **reference-bearing** job (the overwhelming default, per D2/FR-18) to `gpt-image-2-image-to-image`, and only **reference-free** jobs (moderation fallback, failed style-reference uploads) to `gpt-image-2-text-to-image`. Full input surface in Section 8c. Resolution (1K/2K/4K) and aspect ratio per platform/format come from config.
- **Seedance 2.5** (Kie model id `bytedance/seedance-2-5`) — generates reels. Text-to-video and image-to-video (seed frame, **D18**), with native AI audio (**D22**). 9:16 vertical, short duration. Per-unit price is still unpublished by Kie, so reel planning stays blocked until `price_per_unit.reel_second` is set in config (Section 11). Motion references removed (v2.0.0); reels render from seed frame and style references only.

**Async, concurrent, per-job isolation.** Per **D5**, once a batch is submitted the engine polls all jobs concurrently (`asyncio.gather`), never serially. The poll interval is `poll_interval_s` (default **3**, canonical in `30-configuration-and-run.md`); per-job timeouts are `image_job_timeout_s` (default **600**, canonical in `30-…`) and `video_job_timeout_s` (1800, canonical in `30-…`; raised 300→600→1800 in v1.6.7–v1.6.9 as measured Seedance renders grew to 302–378 s initially, then hit 600 s ceiling in W6 acceptance test; image timeout raised 180→300 in v2.1.1 after the 2026-08-13 broken-baseline run lost slides at ~180 s, then 300→600 in v2.1.3/D48 after run 20260813_222101_g1xt lost 2 slides at the 300 s ceiling). Three seconds is the deliberate middle: fast enough that a 20-second image isn't sitting finished and unnoticed, slow enough that a five-minute reel window doesn't cost hundreds of status calls. After a job's first 60 seconds of pending, its own poll interval widens to ~10 s — reels spend most of their life in that regime; images are unaffected. Note: `run_deadline_min` (default **60** min, canonical in `30-…`; this line said 25 until v2.4.0 and was stale by two raises) must exceed `video_job_timeout_s` for a reel run to reach its own timeout ceiling.

**A failed poll is never a failed job.** `http_max_attempts` governs `createTask` and file-upload calls **only**. A `recordInfo` poll that errors (network drop, 5xx, timeout) is simply retried at the next poll tick — with backoff on 429/5xx — indefinitely, bounded solely by the job's own timeout and `run_deadline_min`. The alternative reading (three failed polls = failed job) would let a 30-second router reboot mark every concurrently-polling paid job failed at once while the results sit finished at Kie; that reading is explicitly wrong.

**Image-job resubmit on timeout or non-moderation failure (FR-317).** A carousel slide or standalone image job that ends in TIMEOUT or a non-moderation FAILURE is automatically resubmitted **exactly once** as a discretionary reservation, priced like any render. A second timeout (or second failure) is final: the slide is lost, billed $0 for the timed-out attempts (existing reconcile behavior), and reported loudly. The resubmit ledger is separate from the vision-check retry (NFR-4) — a slide may use both. Video jobs remain: timed-out video jobs are never resubmitted (Section 8, FR-44 survival for video). There is still never a second poll window for the *same* task id; resubmission is a new job.

**Polling measures elapsed time with a monotonic clock**, never wall-clock time. A workstation run is exactly the environment where the machine sleeps, hibernates, resumes, or has its clock corrected mid-run; a wall-clock timeout would declare a healthy job "stuck" purely because the laptop lid was shut. Elapsed-time accounting for both the per-job timeout and `run_deadline_min` uses the monotonic source.

**Three job outcomes, not two.** A stuck/failed job fails only that job — logged and skipped — never the batch. But "failed" is not only `state: fail`:

1. **Fail** — `recordInfo` returns `state: fail` with `failCode`/`failMsg`. Classified (moderation/policy vs transient) per Section 10.
2. **Stuck** — no terminal state within the per-job timeout. Logged with the job id and the timeout value exceeded.
3. **Success with an unusable result** — `state: success`, but `resultJson.resultUrls` is **empty, missing, malformed, or points at a URL that cannot be downloaded** (404, dead host, zero-byte body, non-image/video content). This is treated **identically to a failed job**: the creative is skipped, the spend is still counted (it was submitted — see the budget rules in `10-pipeline.md`), and the log line names the sub-cause (`empty_result_urls` / `result_url_unreachable`) rather than laundering it into a success. A green status code with nothing behind it is the most dangerous failure shape precisely because it looks fine — naming it is the point.

**Error codes worth naming.** Two failure shapes get distinct handling rather than falling into a generic "job failed" bucket: HTTP 402 (insufficient Kie balance) is a whole-run condition, not a single-job one — a retry cannot fix it, so the run reports "top up Kie credits" and skips all remaining render submissions; HTTP 429 (rate limit) gets the same bounded backoff as every other integration — `http_max_attempts`, default 3 (Section 2, NFR-14).

**No generation seed.** Kie.ai's `recordInfo` response exposes no generation seed or job parameters for either model — renders are not reproducible from the API alone (this closes the earlier open question). Every asset's meta file states this plainly rather than promising reproducibility.

- **FR-42**: The engine SHALL submit image and video generation jobs to Kie.ai using its async job model — concurrent `createTask` calls, since Kie.ai has no dedicated batch endpoint — polled together via `recordInfo`.
- **FR-43**: The engine SHALL poll all in-flight Kie.ai jobs concurrently; poll interval (`poll_interval_s`, default 3) and per-job timeout (`image_job_timeout_s` default **600**, `video_job_timeout_s` default **1800**) SHALL be configurable.
- **FR-317** *(v2.1.3, D48; amended v2.2.0, D49/D51)*: An image job (carousel slide or standalone image) that ends in TIMEOUT or non-moderation FAILURE SHALL be automatically resubmitted exactly once as a discretionary reservation, priced like any render; a second timeout or failure is final (the slide is lost, billed $0 for timed-out attempts, reported loudly). The resubmit ledger is separate from vision-check retries (NFR-4) and from gauntlet re-renders. **Exceptions (never resubmittable):** `NO_RUNWAY` refusals (per D51) and gauntlet-round failures (FR-322–330) are not resubmittable events — gauntlet re-renders are always fresh submissions on their own ledger rows with no second poll window for the original task id; gauntlet pass/fail verdicts stand as terminal. Video jobs remain: timed-out video jobs are never resubmitted (FR-44 survival). There is still never a second poll window for the same task id — resubmission is always a new job.
- **FR-44**: A Kie.ai job that times out or returns a failed status SHALL fail only that job's creative, logged and skipped, without aborting or delaying the rest of the batch. **Video jobs that time out are never resubmitted** (FR-317 exclusive to image jobs); image-job resubmit policy is owned by FR-317. The creative is marked failed and its actual (Kie-reported) cost is reconciled to the budget, not the full estimate.
- **FR-242**: A Kie.ai job reporting `state: success` whose `resultJson.resultUrls` is empty, missing, malformed, or not downloadable SHALL be treated identically to a failed job — creative skipped, spend counted, logged with the distinguishing sub-cause — and SHALL NOT be recorded as a successful render.
- **FR-243**: Kie.ai poll scheduling and all job/run timeout accounting SHALL use a monotonic clock, so host sleep, hibernation, resume, or wall-clock adjustment cannot cause a healthy job to be declared stuck.
- **FR-167**: A Kie.ai HTTP 402 (insufficient balance) response SHALL be treated as a whole-run condition — reported as "top up Kie credits" — and SHALL skip all remaining render submissions rather than retrying.
- **NFR-13** *(amended v2.5.1, D60)*: Image resolution/aspect ratio (GPT Image 2) and resolution/duration (Seedance 2.5) SHALL be configurable per platform/format combination. Per-platform image tier is `platforms.<name>.image_resolution` (FR-342).

The meta-style registry supplies textual style guidance, not reference images (D46 — see §8c risk note). It is one upload path serving briefs and generated artifacts only.

**OQ-5 is closed (2026-08-09).** The file-upload API exists and is documented: `POST https://kieai.redpandaai.co/api/file-stream-upload` (multipart binary, for large files; params `file`, `uploadPath`, optional `fileName`), plus an upload-from-URL endpoint and a base64 variant (<10 MB). Note the host is `kieai.redpandaai.co`, **not** `api.kie.ai`. **Hard constraint: uploads are temporary — Kie's quickstart states auto-deletion after 24 hours.** Harmless for same-run attachment (render jobs submitted within the run window), but an upload URL cannot be reused by a later run or a re-render — anything touching Kie-hosted URLs later must re-upload (tracked with OQ-20 in `00-overview.md`).

**Brief-image upload memo (run-scoped).** A run maintains a `dict[Path, str]` mapping local brief-image file paths to their Kie-uploaded URLs. Each distinct file is uploaded once per run; subsequent jobs on the same topic reuse the URL from the memo. The memo is run-scoped only — a later run re-uploads.

**Per-image upload failure** (brief images) removes that image only — the job proceeds with the remaining brief references and the failure is logged with the local filename and the upload error. A job whose brief references *all* fail to upload still renders with text guidance alone (no brief URLs attached).

**Failure anywhere degrades, never blocks.** A failure at any step — upload fails, path not found — degrades that job's reference set, logged with the specific step that failed. It never fails the whole creative or the batch.

- **FR-200 (implicit)**: The engine SHALL maintain a run-scoped upload memo (`dict[Path, str]`) deduplicating local brief-image uploads to Kie; each distinct file uploads once per run; subsequent jobs on the same topic reuse the cached URL.
- **FR-244 *(amended v2.1.3, D48)***: **Brief-supplied reference images** SHALL be uploaded via Kie's file-upload API to obtain public URLs before attachment to render jobs; a per-image upload failure SHALL remove only that image, be logged with filename and error, and SHALL NOT prevent the job from proceeding with its remaining references. **Narrow carve-out (v2.1.3):** small logo/tool-mark patches **cropped from source slides** (per FR-315 mark-box extraction) MAY be uploaded to Kie as render references — this is the **ONLY sanctioned upload from `output/<run>/source/`**. Full source slides, panels, or any other crop remain forbidden, and no Virlo CDN host may ever appear in any render payload (unchanged). The Virlo source-slide archive itself (`source.yaml`, full `slide_NN.jpg` files) is analysis-only (FR-306, gallery-only per FR-72/FR-309).
- **FR-249**: Scratch-directory files produced during a run (if any) SHALL be deleted at end of run on every exit path; the `output/` folder SHALL remain untouched by this cleanup (FR-86), and a cleanup failure SHALL be logged as a warning without failing the run (withdrawn: working-directory video files — motion references deleted).

### 8d. Slide intelligence — post-Confirm analysis of carousel source posts (FR-306, v2.1.0; amended v2.1.2, D-A, D-C)

**Scope and timing.** Slide intelligence runs **after the Confirm gate, before COPY** — it is a paid LLM spend and its cost is estimated pre-Confirm from panel counts (§0.11). It executes once per assigned carousel source post (≤6/run, typically 1–2); reels and one-off images skip this stage. Virlo's `panel_texts` are preferred as verbatim text sources; vision analysis fills gaps (`vision_transcribed` tag).

**The analysis call.** One OpenRouter StructuredCall with `anthropic/claude-sonnet-5` (analysis role) receives all slide images from an assigned source post and returns per-slide:

- **`onimage_text`** — verbatim transcription of any visible text IN the slide content (charts, labels, callouts, product text, captions). Source: Virlo `panel_texts[i]` if present (position-matched); vision fills gaps (`vision_transcribed` provenance). Never synthesized or paraphrased. Does NOT include creator chrome.
- **`chrome_text`** — verbatim transcription of creator chrome ONLY: @handles, URLs, watermarks, page counters ("3/6"), swipe cues. Extracted separately so on-image text is "real content" and chrome is clearly marked. Never rendered on-image in output; consumed by FR-312 (creator-identity and chrome-echo strip at offer/panel-map stage before copy selection).
- **`visual_brief`** — concise description of graphics, charts, icons, composition, layout (e.g., "line chart, three series, ascending", "four icons in a grid", "hero image + centered text"). **Always in English** — render prompts are English; on-image text stays source-language. Driven by slide image content, never by Virlo metadata.
- **`brand_marks`** — list of names/descriptions (≤10 entries, ≤120 chars each) of logos, wordmarks, or watermarks visible in this slide, as detected by vision. Names, not a boolean, because the list is **consumed downstream** in two ways: (1) competitor-blocklist matching (§0.12) — competitors are genericized, never reproduced (`10-pipeline.md` FR-308 applies the filter); (2) **tool-mark sanction listing (FR-310, D-A)** — third-party tools named in brand_marks are rendered as real, recognizable logos in their true brand colors, exempt from style palette discipline. An empty list means no marks seen. Vision analyses at most **20 slides per post** — a cost fence, since `image_urls` is source-controlled and unbounded decks would be spend the Confirm-gate estimate never quoted; slides past the cap keep their position and Virlo text, and the cut is warned (`slide_intel_slides_capped`).
- **`mark_boxes`** *(v2.1.3, D48)* — for each visible tool/brand mark: its name, the slide it appears on (slide position, 1-indexed), and a fractional bounding box `[x, y, w, h]` in 0–1 image coordinates (origin top-left). **Cap 24 per deck** *(raised from 10 after the glz0 audit, D48 follow-up: a tool round-up deck carried 21 distinct real marks and eleven shipped with no patch)*. An empty list means no boxes detected. Used to crop and upload patches as render references (FR-315, FR-244). Fail-open: detection failure yields an empty list, not a failed call.

**Brand safety (hoisted from §0.12, v2.1.2).** The `brand_marks` field enables fidelity to real logos while protecting against competitor promotion. **Competitor marks** — entries matching `branding.competitors` blocklist — are genericized in the render instruction ("a generic chat-app logo shape"), never reproduced or named. **Tool marks** — third-party products named in the on-image text (Claude, Notion, Canva, etc.) or detected in brand_marks — render as the real, recognizable wordmark in true brand colors (FR-310). **Platform chrome and creator identity** — @handles, watermarks, follower counters, platform UI (Swipe cues, TikTok watermark, etc.) — are stripped at offer time per FR-312 and never rendered. This three-layer structure (competitor strip, tool honor, chrome excision) lets the engine preserve real product references while excluding sources' self-promotion and platform branding.

**Known limitation: Virlo OCR artifacts persist.** When Virlo supplies `panel_texts` (e.g. OCR'd "Al" for "AI"), it wins over vision transcription per the never-overwrite rule (FR-100), so artifacts ship verbatim.

**Prompt file.** `prompts/slide_intel_question.md` carries the structured query and instruction set, versioned and parity-tracked under FR-174. The prompt ensures analysis-role reasoning produces faithful transcriptions and visual descriptions suitable for render-prompt construction.

**Data storage.** Slides are downloaded via the packager's existing client (one download, two uses: vision input + gallery reference) into run-level `output/<run>/source/<post_id>/` as `slide_NN.jpg` (indexed 1-based, matching panel positions). Metadata is written to `source.yaml`:

```yaml
post_id: <id>
url: <virlo_url>
author: <author>
published_at: <ISO 8601>
views: <int>
panel_count: <int>
slides:
  - position: 1
    virlo_text: "..." (if panel_texts[0] present)
    vision_text: "..." (transcription of slide content from analysis)
    chrome_text: "..." (transcription of creator chrome: @handles, URLs, watermarks, counters)
    visual_brief: "..." (analysis output)
    brand_marks: ["AcmeAI wordmark", "TikTok watermark"]   # names, [] when none
    vision_transcribed: true|false (tag when Virlo panel was absent)
    image_file: slide_01.jpg
vision:
  model_role: analysis
  model_id: <resolved model string>
  status: ok | vision_unavailable | vision_disabled
  reason: <stable warn key when degraded, else absent>
```

**Failure modes (fail-open, never aborts per §0.14c).** (a) Analysis call fails/times out → keep Virlo `panel_texts`, tag as `vision_unavailable`; creatives render with panel text only, no visual briefs. (b) Download 404 (source image unreachable) → that slide has no source image in the gallery; brief slot is absent. (c) Fewer briefs than slides → align by position, missing = absent; truncation tagged `panels_truncated` if source `panel_count > carousel_slides ceiling`. Every degrade is logged with the specific step and post id; the creative continues with what remains.

**Antipattern: Virlo bytes in render payloads.** This stage is analysis-only: `source/` outputs are never uploaded to Kie or any external service, never quoted directly in render prompts as "use this exact text", and never appear in `render.upload_file` boundary. Render prompts use `visual_brief` (English description of slide content) and `onimage_text` (verbatim transcription of visible text) — both derived from vision analysis or original source panel text, never Virlo URL or metadata. The hard rule: **no Virlo URL or byte in any render payload** (§0.11 evidence for D46).

- **FR-306 *(amended v2.2.0, D49–D53, v2.7.0, D63)***: Post-Confirm, the engine SHALL run an analysis-role Claude Sonnet 5 call via OpenRouter for each assigned carousel source post, receiving all slide images and returning **one optional deck-level `language` field** (ISO 639-1 code of the language the slides' words are written in, `""` when absent or mixed/undetectable) alongside per-slide transcriptions (`onimage_text`, `chrome_text`), visual briefs (`visual_brief`), brand-mark detection (`brand_marks`), and mark bounding boxes (`mark_boxes` — name, slide position, box in 0–1 coords, **`kind: tool|apparel|chrome|other` classification**, cap 24 per deck, raised from 10 after the glz0 audit). **Transcriptions pass the OCR repair boundary:** both `onimage_text` (Virlo-preferred per §0.11) and vision-transcribed text receive the identical logged uppercase-token-scoped confusable repair (e.g. "l"→"I", "O"→"0") at admission; `vision_text` in `source.yaml` records both original and repaired bytes; FR-100 verbatim-verification applies to the admitted bytes. **Truncation detection:** panels with trailing-ellipsis or mid-word cut heuristics carry `truncation_suspect: true` in `panel_map` for downstream use by the brief critic (FR-322). Downloads SHALL be stored in `output/<run>/source/<post_id>/` (packager deduped, gallery-only). The prompt template SHALL be `prompts/slide_intel_question.md` (FR-174 parity-tracked). **`brand_marks`, `mark_boxes`, and `chrome_text` are consumed downstream:** `brand_marks` + `mark_boxes` feed FR-310 (tool-mark sanction) and competitor-blocklist matching; `chrome_text` feeds FR-312 (creator-identity/chrome strip at offer stage). `mark_boxes` with `kind: tool` specifically feed FR-315 (logo patch extraction — only tool marks croppable); other kinds are informational only. **`language` feeds FR-343:** the rung-2 deck-level reading that is part of the language ladder (FR-343) for determining whether translation is needed. Failure modes SHALL be fail-open per §0.14c (vision unavailable, download 404, alignment gaps, detection failure); the estimator SHALL include a `slide_intel` line pre-Confirm. **No Virlo URL or byte SHALL ever appear in any render payload — source analysis informs render prompts via visual briefs and transcriptions only.** Cross-reference: FR-303 (`description` context-only), FR-308 (visual-brief rendering in slide prompts), FR-310 (tool-mark fidelity), FR-312 (creator-identity strip), FR-315 (logo patch extraction), FR-322 (gauntlet brief critic), FR-343 (translate pipeline, language ladder).

### 8e. Gauntlet critics — post-render quality gate via OpenRouter (FR-322–330, v2.2.0)

**Role and timing.** The gauntlet is a three-critic quality gate that runs **after render completion** via OpenRouter with the `critic` role. Each critic examines rendered frames against contract data (expected text, layout zones, style DNA, mark requirements) and returns defect verdicts in strict JSON. The stage is enabled by `run.gauntlet.enabled` (default true); disabling it bypasses all critic checks (legacy FR-105 path is deleted). Gauntlet runs are keyed by rounds (per FR-324) and bounded by `run.gauntlet.deck_budget_usd` (default 0.30) per creative, with runway and deadline gates per D51.

**Three independent critics, per-critic roles (FR-322).** Each critic judges rendered frames independently, receiving no prior-round verdicts and no sibling verdicts within a round:

| Critic | Judges | Enum codes |
|---|---|---|
| **`brief`** | Contract fidelity + leakage (text presence, invented text, translation, pair binding, marks) — PRESENCE, never quality | `missing_text`, `invented_text`, `translated`, `pair_break`, `missing_mark`, `forbidden_mark`, `platform_chrome`, `identity_leak`, `counter_value`, `signature` |
| **`system`** | Style contract + cross-frame consistency (palette, layout, counter placement) | `style_palette`, `style_layout`, `style_consistency`, `counter_placement` |
| **`craft`** | Execution quality (legibility, contrast, logo fidelity, composition) — EXECUTION, never content | `garbled`, `truncated`, `contrast`, `logo_fidelity`, `composition`, `frame_integrity` |

Each critic receives: rendered frame(s) as image(s), per-frame contract fields (`body_lines`, `counter`, `signature`, `is_list`), deck-level contract fields (`required_marks`, `forbidden_terms`, `style_dna`, `layout_zones`, `list_mode`, `sanctioned_illegible`, `platform`), and frame index. **Frames are loaded through the shared image loader** (`vision_check.load_images`), whose source union is a local file path (rendered deck slides and standalone images) **or** a Kie result URL (the reel seed frame); images go at native resolution, never downscaled, and an unreadable frame is dropped and re-mapped via the loader's attachment positions — a critic's `frame` value is a 1-based attachment slot, re-mapped by the engine to the slide number. The structured call uses `models.critic` (default `anthropic/claude-sonnet-5`) with a maximum of 8,000 completion tokens per call.

**Output schema — strict JSON (per-critic call, one call per critic per round).** Each critic returns a JSON response with the following structure (enforced by the structured-output mode):

```json
{
  "frames": [
    {
      "frame": 1,
      "pass": true,
      "defects": [
        {
          "code": "missing_text",
          "zone": "top|upper|middle|lower|foot|left|right|centre|chip|card|full_frame",
          "confidence": "high|low",
          "detail": "<= 200 chars>"
        }
      ]
    }
  ]
}
```

**Bounds:** ≤3 defects per frame, ≤8 defects per call (critic call), exactly one entry per attached image (no missing and no extra frame rows). `craft` defects with `confidence: low` are recorded but do NOT fail the frame (audit tag only). A verdict of `pass: false` carrying an empty `defects` list is a self-contradicting row: it SHALL be logged `critic_empty_fail` and **treated as a pass** — a critic that cannot name a defect has not found one.

**Unavailable critic handling.** A critic call that returns unparseable JSON, times out, or errors is retried **exactly once** at the content level (NFR-14's content-retry cap; `http_max_attempts` governs only the underlying transport call). If the retry also fails, the critic is dropped **for the whole deck**, not just the round: `degraded_gate` is set, `gauntlet_critic_unavailable` is logged with the critic name and error, and every remaining round is judged on the surviving critics. **All enabled critics unavailable** ⇒ the gauntlet returns result `skipped` — the creative ships as-is, tagged, and is **never** BLOCKED (a broken gate must not cost the operator a paid deck).

**Model resolution.** The `critic` role resolves to `models.critic` from config; if unset or unresolved, it falls back to `models.analysis` (itself defaulting to `anthropic/claude-sonnet-5`). No critic call is placed if the model is unknown (caught at pre-flight config validation).

- **FR-322** *(integration side; owned by `10-pipeline.md`)*: Three independent critics (`brief`, `system`, `craft`) SHALL judge rendered frames post-completion via OpenRouter with the `critic` role, receiving the frames and contract data only — no assembled render prompt, no reference set, no prior-round verdicts, and no sibling verdicts within a round (the only style referent is the `style_dna`/`layout_zones` wording, which is stated honestly). Each critic call is one multi-image StructuredCall returning strict JSON with per-frame defects (code, zone, confidence, ≤200-char detail); the per-critic enum is enforced in-schema (`brief`: presence/leakage codes, `system`: style/consistency codes, `craft`: execution codes). An unavailable critic (unparseable, timeout, error) is retried once, then dropped for the deck with `degraded_gate` + `gauntlet_critic_unavailable`. All enabled critics unavailable ⇒ result `skipped` (ship as-is, tagged), never BLOCKED.
- **FR-328** *(integration side; owned by `10-pipeline.md`)*: Per-round per-frame per-critic verdicts, critic token cost, and terminal outcome SHALL be persisted in `meta.yaml.gauntlet` and logged on every terminal path via the events owned by `40-outputs-and-logging.md` (`gauntlet_round`, `gauntlet_rerender`, `gauntlet_blocked`, `gauntlet_budget_stop`, `gauntlet_deadline_stop`, `gauntlet_critic_unavailable`, `gauntlet_fix_truncated`, `critic_empty_fail`).

Secrets are supplied via environment variables, loadable from a local `.env` file, never committed and never hardcoded:

| Variable | Used by | Missing-key behavior |
|---|---|---|
| `VIRLO_API_KEY` | Virlo MCP wrapper (Section 3), REST calls to `api.virlo.ai` | Run aborts at pre-flight — no trend data means no run is possible. |
| `NOTION_TOKEN` | Integration secret for the self-hosted, token-based Notion MCP server (stdio, Section 5) | `notion_influence` is forced to `off` for the run with a clearly logged warning; run proceeds without brand context. |
| `POSTIZ_API_KEY` | Postiz's public API key (Settings → Developers → Public API on the operator's instance); used by the Phase 2 REST publisher (Section 6) for `Authorization: <key>` and, optionally, by Postiz's MCP ops seam | N/A in MVP; Phase 2 `--publish` refuses to run without it. Not required for MVP generation runs at all. |
| `POSTIZ_BASE_URL` | Base URL for the Phase 2 Postiz REST publisher; defaults to `https://api.postiz.com/public/v1` (hosted cloud, 60-publishing FR-225); a self-hosted URL works too | N/A in MVP; Phase 2 uses the default when unset — never a refusal. Not a secret in the credential sense, but env-sourced alongside the key. |
| `OPENROUTER_API_KEY` | OpenRouter REST (Sonnet 5, GPT 5.6 Luna) | Run aborts at pre-flight — no analysis or copy is possible without it. |
| `KIE_API_KEY` | Kie.ai REST (GPT Image 2, Seedance 2.5) | Run aborts at pre-flight — nothing can be generated without it. |

A missing key degrades only the features that need it, loudly and early, never silently. Keys structurally required for any output (Virlo, OpenRouter, Kie.ai) cause a pre-flight abort. Keys gating an optional feature (Notion, Postiz) degrade or refuse that feature only.

**Secrets hygiene is absolute (D30).** Every key in the table above lives only in `.env` or real environment variables — never committed, never hardcoded. Crucially, a key is **never interpolated into any LLM prompt or template** and **never sent to any model**: the prompt-template layer (`prompts/`, `briefs/`, `10-pipeline.md`) has no placeholder that could resolve to a secret value, so a key cannot leak through the Analyze/Write generation path even by accident. Keys flow into exactly two places: an HTTP `Authorization`/API-key header for REST calls (OpenRouter, Kie.ai, Postiz), or a per-server MCP environment dict for stdio servers (Section 2). Because run.log and events.jsonl log full request payloads and prompts for debuggability, redaction is the deliberate backstop, not the primary defense — every logged payload is scrubbed of Authorization headers and key-shaped values at the logging boundary before it is written, per `40-outputs-and-logging.md`'s FR-152.

- **FR-45**: The engine SHALL validate required secrets at pre-flight, before any MCP session is opened or any paid API call is made.
- **FR-46**: Missing `VIRLO_API_KEY`, `OPENROUTER_API_KEY`, or `KIE_API_KEY` SHALL abort the run at pre-flight with a clear, specific error identifying the missing key.
- **FR-47**: Missing `NOTION_TOKEN` SHALL force `notion_influence` to `off` for the run and SHALL log a clear warning, without aborting the run.
- **NFR-112**: No API key SHALL ever be interpolated into an LLM prompt/template or sent to any model; every key SHALL flow only into HTTP auth headers or per-server MCP environment dicts, with logged payloads redacted at the logging boundary per `40-outputs-and-logging.md` FR-152.

## 10. Failure modes per integration (transport-level)

Per the shared philosophy: **degrade and report, never block the whole run.** This file owns **transport-level** failure behavior only — what happens at the MCP/REST/network boundary. Plan-level consequences (which creative gets skipped, how a batch degrades, which trend gets dropped) are owned by `10-pipeline.md` §10; output-only cases (disk, gallery, interrupted-run packaging) are owned by `40-outputs-and-logging.md`. Rows are not duplicated across files — cross-reference instead.

| Failure | Scope | Behavior |
|---|---|---|
| MCP server won't start (stdio subprocess fails to launch) | That integration's session | Logged as a startup failure; per-integration consequence (abort vs. degrade) owned by `10-pipeline.md`. |
| MCP startup timeout (server too slow to become usable) | Same as above | Distinct from a launch failure and from a per-tool-call timeout (Section 2); logged with the configured startup-timeout value exceeded. |
| MCP tool call error (server returns an error response) | The single call | Logged with tool name and error; caller treats it as "no data" for that call. |
| MCP call timeout (single tool call) | The single call | Same as a tool call error — logged, treated as no data, no indefinite hang. |
| Virlo wrapper auth error (401/403 → MCP auth error) | That call, likely all subsequent Virlo calls this run | Not retried (a retry cannot fix bad credentials); logged clearly naming `VIRLO_API_KEY` as the likely cause. |
| Virlo wrapper rate-limit (429 → MCP rate-limit error) | That call | Bounded retry with backoff — `http_max_attempts`, default 3 (Section 3); persistent limiting surfaces as repeated no-data. |
| Virlo fails partway through Collect (some monitor ids succeed, later ones error/time out) | Per monitor id | **Per-monitor degrade, never all-or-nothing.** Monitors that answered keep their data; each failing monitor is logged by id with its error class. Collect proceeds to Select with whatever responded. Whether the surviving trend pool is enough to fill the plan is owned by `10-pipeline.md`. |
| Kie file-upload failure for a **local** reference image (style registry / brief-supplied) | That one image | Image dropped, logged with filename and upload error, job proceeds with remaining references (FR-244). |
| OpenRouter 429 / 5xx | The single call | Bounded retry with exponential backoff — `http_max_attempts`, default 3. |
| OpenRouter HTTP 402 (credits exhausted) | Whole run's remaining LLM calls | Recognized once as a run-level condition, **not retried** — every subsequent LLM call would fail identically. Remaining LLM-dependent creatives are skipped with the reason "OpenRouter credits exhausted"; the run packages everything already produced. Reported distinctly from a Kie 402 — Section 7, FR-248. |
| OpenRouter malformed/truncated response | The single call | Tolerant parse attempted first; truncation retried with a higher limit or shorter input; only then does the FR-41 retry cap apply. |
| Notion token expires or is revoked **mid-run** (401/403 on a call, after pre-flight passed) | Each affected Notion call | Distinct from the pre-flight missing-key case (FR-47). Each call returns no data as usual, **but the auth failure is surfaced once as a single clear warning** naming `NOTION_TOKEN` and the fact that brand context is now missing for the rest of the run — not as a silent stream of per-page "no data" lines. One loud warning, not quiet degradation repeated *n* times. |
| Kie.ai job returns a failed status, incl. moderation/policy-class refusal | That one job | Moderation/policy-class failures are detected distinctly from generic transient failures (different status/error shape); the pipeline's fallback (resubmit once without reference images) is owned by `10-pipeline.md` — this file's role is correct classification, not handling. |
| Kie.ai job stuck (never reaches terminal status within timeout) | That one job | Logged with job id and the timeout value exceeded; treated as failed for the plan and **never resubmitted** (Section 8 — it was billed at submission and its `taskId` is in the ledger). Elapsed time is measured monotonically (FR-243), so host sleep/resume cannot fake this. |
| `recordInfo` poll call fails (network drop, 5xx, timeout on the poll itself) | That one poll attempt only | **Never terminal for the job.** The poll is retried at the next tick with backoff; only the job's own timeout or the run deadline can end a pending job (Section 8). A transient network outage therefore delays results, never discards paid work. |
| Kie.ai job **succeeds with an unusable result** (`state: success` but `resultJson.resultUrls` empty, missing, malformed, or not downloadable) | That one job | Treated **identically to a failed job** — creative skipped, spend still counted, logged with sub-cause `empty_result_urls` or `result_url_unreachable`. Never recorded as a successful render (Section 8, FR-242). |
| Reel **seed frame fails to render** (Kie job fail / stuck / FR-242 unusable success) | That reel's overlay text | Detected as an ordinary Kie job outcome and logged as `seed_frame_render_failed`. The consequence — fallback to `in_model` overlay text — is owned by `10-pipeline.md` FR-24. |
| Reel seed frame **rendered, but Seedance rejects its hosted URL** (link expired, host error, non-downloadable body) | That reel | A separate detection from the row above, logged as `seed_frame_url_unreachable` with the provider message — the seed frame rendered and was paid for; the handoff is what broke. Because the rejection is only visible **after** the clip job fails, the consequence is a logged reel failure, not an overlay-text degrade: **the clip is never resubmitted** (operator decision 2026-08-10, v1.7.0 — this keeps §8's sanctioned-resubmission list at exactly two, FR-97 and FR-105). Distinguishing the two rows is what makes "why did this reel fail?" answerable. |
| Kie.ai HTTP 402 (insufficient balance) | Whole run's remaining Kie.ai submissions | Reported plainly ("top up Kie credits"); the run skips all remaining render submissions rather than retrying — Section 8, FR-167. |
| Kie.ai HTTP 429 (rate limit) | The single call | Bounded backoff, same policy as other integrations (NFR-14). |

- **FR-48**: Every integration failure (MCP or REST) SHALL be caught at its call site, logged with enough context to diagnose it, and SHALL degrade only the smallest affected unit of work.
- **FR-49**: No single integration failure other than a pre-flight-required secret or a total absence of trend data SHALL abort an otherwise-healthy run.
- **NFR-14**: All bounded retries SHALL have a hard maximum attempt count sourced from config — no retry path SHALL be capable of looping indefinitely. Transport retries (OpenRouter 429/5xx, Virlo wrapper rate-limit, Kie.ai 429, reference-image download) use `http_max_attempts`, default **3**; content-level retries (OpenRouter malformed-JSON retry per FR-41, and the gauntlet critic retry per FR-322 — which on a second failure drops that critic for the deck rather than retrying again) are capped at exactly **1**. Whole-run conditions (Kie 402 FR-167, OpenRouter 402 FR-248) and unfixable classes (auth, not-found) are **never** retried.

## 12. Render-provider seam & model profiles (D34)

The model market moves faster than this codebase ever will. Two rules keep that from becoming a rewrite every quarter: **every model id is a config string**, and **every render service is reached through one small interface** rather than being wired into the pipeline by name.

**Model ids are configuration, everywhere.** Both model APIs in this file are single-endpoint services. Every OpenRouter model — the analysis model, the copy model, the vision-check model — is reached through the same chat-completions call (Section 7); every Kie model — images, carousel slides, seed frames, reels — is reached through the same `createTask` call (Section 8). Between one model and the next, the only thing that changes is the id string in the request body. So ids live in config and nowhere else (canonical keys owned by `30-configuration-and-run.md`, FR-280 block): no engine module, prompt template, log line, or cost table contains a literal model id, and none branches on one. Swapping a model for a sibling that behaves the same way — the reel model from `bytedance/seedance-2-5` to a faster or cheaper variant of the same family, or the vision/analysis role from Sonnet 5 to another OpenRouter vision model — is a **config-only change**: no code touched, no new profile written, because the sibling shares the profile it swapped into.

**The render-provider seam — exactly four operations.** All render traffic crosses one interface, and it is deliberately tiny:

1. **Submit a render job** — a model id plus the assembled inputs go out; a job handle comes back.
2. **Poll a job's status** — waiting, succeeded, or failed, with the provider's own failure reason carried through intact.
3. **Retrieve result URLs** — the public link(s) to the finished asset(s), or their honest absence.
4. **Upload a local file, receive a public URL** — the single door from local bytes to something a renderer can reference (Section 8b).

**Kie.ai is the only implementation built** — `createTask`, `recordInfo`, and the file-upload API, exactly as Sections 8 through 8c specify. Everything above the seam (Generate, the seed-frame chain, the carousel anchor chain, budget accounting, packaging) speaks only these four operations. Kie's field names, its `resultJson` shape, its state vocabulary, and its HTTP status codes stay *behind* the seam; the three-outcome classification — fail, stuck, success-with-unusable-result (FR-242) — is something the seam reports, not something each caller re-derives from raw provider JSON. A second provider is therefore an additional implementation of four operations, never a fork of the pipeline.

**Model profiles.** An id alone doesn't tell the engine how to talk to a model — providers disagree about what to call a prompt, a reference, a ratio, or a duration, and about how many references they will accept. So each render model the engine supports carries a small **profile** declaring three things:

- **Parameter mapping** — what this model calls each of the engine's standard render inputs: prompt text, reference images, aspect ratio, resolution, duration, audio. The engine assembles one standard input set; the profile renames it for the provider.
- **Reference limits** — how many reference images and videos the model accepts, plus any per-file or total size/duration ceilings, so the engine caps at the model's real limit instead of learning it from a rejected job.
- **Which prompt template set it uses** — the family of prompt scaffolds the model is written for. Template sets themselves are owned by `50-promptcraft.md`; the profile only names the one it uses.

Two profiles ship: **`gpt-image-2`** (input surface in Section 8c) and **`seedance-2-5`** (Sections 8a and 8b). A configured model id that resolves to **no known profile** is caught at **pre-flight**, never at render time: the run refuses to start, naming the offending config key, the model id found, and the profile that would have to be added — and exits with the pre-flight-refusal exit code **2** (`30-configuration-and-run.md`). There is no silent fallback to another model's parameter names and no half-spent batch discovering the gap on job three.

**Adding a new model family — the one-page recipe.** Bringing in a Kling, a Veo, or the next thing entirely is additive work, not an engine rewrite:

1. **Check the provider.** If the family is served by a provider the seam already speaks to (today: Kie), skip to step 2. If not, write one more implementation of the four operations above — that is the whole provider-side task.
2. **Write the profile.** Name the family's parameters for the standard inputs, its reference limits, and the prompt template set it will use.
3. **Write that prompt template set** in `prompts/`, per `50-promptcraft.md`. A model family fed another family's prompt conventions is the usual reason a "simple swap" produces bad output — the templates are half the profile's value.
4. **Register its price** in `price_per_unit` so the estimator can plan it. A family with no configured price refuses to plan, exactly as reels do today while the reel unit price is unset (Section 8, OQ-2).
5. **Point the config's model key at the new id.**
6. **Prove it on one item** — a small run, compared in the gallery against the references shown alongside.

No engine module appears in that list, and that is the test: if adding a family requires editing Generate or the budget code, the seam has been violated and the fix belongs in the seam, not in the caller.

- **FR-270**: Every model identifier — OpenRouter chat model ids and Kie model routes alike — SHALL be sourced from config; no model id SHALL be hardcoded in engine code, prompt templates, or logging. Exception: profile declarations (which define how to talk to each model family) and price-table family keys (e.g., `sonnet`, `luna`, `gpt-image-2`, `seedance-2-5`) are sanctioned homes for literal model family names and route identifiers, never branch points in engine logic. Swapping a model for one that resolves to the same profile SHALL require a config edit only.
- **FR-271 *(amended v2.1.0)***: All render traffic SHALL pass through a single render-provider interface exposing exactly four operations — submit render job, poll job status, retrieve result URLs, and **upload brief images / generated artifacts (never `source/` files) to obtain a public URL**. Kie.ai SHALL be the only implementation built; no pipeline code SHALL depend on Kie-specific request fields, response shapes, state vocabulary, or status codes directly.
- **FR-272**: Every render model SHALL have a profile declaring (a) the provider's parameter names/mapping for the engine's standard inputs (prompt, references, ratio, resolution, duration, audio), (b) its reference limits, and (c) the prompt template set it uses (`50-promptcraft.md` owns the sets). Profiles for `gpt-image-2` and `seedance-2-5` SHALL ship. A configured model id resolving to no known profile SHALL cause a pre-flight refusal naming the config key, the model id, and the missing profile, exiting with code 2 — never a runtime failure mid-batch and never a fallback to another profile's parameter names.
- **FR-273**: Adding a new model family SHALL require only a new profile, a matching prompt template set, a registered per-unit price, and a config edit (plus a new provider implementation of FR-271's four operations if the family is not on an already-supported provider) — and SHALL NOT require changes to the Generate stage, the polling loop, or budget accounting.

### 12a. Higgsfield.ai vs Kie.ai — the provider comparison, re-verified 2026-08-09

Higgsfield.ai was researched twice as a candidate second render provider and remains deliberately **not built**. The full comparison is recorded here so the question isn't re-argued from memory:

| Requirement | Kie.ai (built) | Higgsfield (parked) |
|---|---|---|
| Headless auth | `Authorization: Bearer <key>` end to end | MCP is **OAuth browser login only** ("no API keys", official page); CLI needs a one-time browser login; the legacy SDK's `Key id:secret` REST covers only old routes |
| Seedance 2.5 | **Live, full tier** — 4–30 s, reference videos ≤30 s total, reference images ≤30, reference audio, `generate_audio`, webhooks | **Still waitlist** — their own product page says "doesn't have access to Seedance 2.5 yet" despite a launch-styled blog post; their API for it is pre-launch |
| Reference-bearing image model | GPT Image 2 image-to-image, `input_urls` ≤16 | GPT Image 2 served in-app; no published API route |
| File upload (local bytes → URL) | Dedicated API, three methods (§8b) | None documented |
| Model-path catalog | Complete, public (docs.kie.ai) | **Not published** — SDK documents only legacy Soul/Flux/DoP/Speak routes; current programmatic surfaces are MCP + CLI |
| Pricing | Pay-per-task, prepaid **non-expiring** credits, published unit prices, failed generations not charged | Subscription with **monthly-expiring credits** ($15–99/mo); Seedance 2.5 quoted at ~65 credits per 10 s 720p (≈$3.25) vs ~$0.57 for comparable Seedance on Kie — roughly **5–6× the render cost** |
| Unique upside | Breadth of routes incl. `reference_audio_urls` and `return_last_frame` (the two D35 parked capabilities are *Kie* primitives, not Higgsfield exclusives) | Soul trained character consistency (brand mascot/persona), Cinema Studio camera/lens control, one-login access to Sora 2 / Veo 3 / Kling 3 |

**Conclusion (unchanged, now firmer):** Kie-only remains correct. Higgsfield is a **named future adapter behind FR-271's interface** — no config key, no stub, no code. Revisit is tracked as **OQ-18** (`00-overview.md`), now with **three** named conditions, all required: (a) a public REST API or API-key-authenticated MCP with a published model-path catalog covering Seedance 2.5; (b) published per-unit pricing or a pay-per-use tier; (c) a concrete need for what it uniquely unlocks — Soul character consistency, Cinema Studio control, or Sora/Veo/Kling as fallback renderers. Until all three hold, its cost model and interactive-only auth are structurally incompatible with an unattended, pay-per-use pipeline.

## Design Decisions

- **D1 — True MCP for content services, direct REST for inference — with one evidence-based exception.** Virlo and Notion are content/data systems with structured, evolving APIs best served by a standard protocol with typed tools and a shared client, and that holds cleanly for both. OpenRouter and Kie.ai are stateless inference calls — wrapping them in MCP would add a protocol hop with no benefit. Postiz was originally slotted into the same "content service, therefore MCP" bucket by design intent alone; live research into Postiz's actual MCP tool surface (D29) showed its official server has no way to accept externally generated media, so the philosophy is kept and the implementation is amended: Postiz's publishing path runs over its public REST API, with MCP retained only as an optional ops-query seam (Section 6). This is a documented, evidence-based exception to one vendor's API shape, not a reversal of the split itself — the split still keeps the codebase small (one MCP client layer, not several bespoke integrations) while keeping the fastest, and now the *only working*, path for the calls that must carry real files.
- **D5 — Everything concurrent, batch-submitted, polled with `gather`.** The old system's 93 blocking job-status polls and serialized 5–11-call chains per image are exactly what a 19-minute, 3-image run looked like. HypeSocials submits whole batches at once and polls them together, so wall-clock time is bounded by the slowest single job. This is why FR-42/FR-43 exist as hard requirements, not just an implementation preference.
- **D7 — Notion influence is a knob, not a default.** Brand grounding was one of the old system's heaviest, most opaque subsystems (a hand-copied YAML snapshot masquerading as live data). HypeSocials defaults to `off`, fetches live via real MCP only when asked, and now truncates rather than summarizes what it fetches (Section 5) — one fewer LLM dependency, deterministic cost, same goal of keeping prompts lean.
- **D16 — Every file opens with a TL;DR.** Reviewers and future collaborators need a 30-second, jargon-free entry point before the requirement-numbered detail. This file's TL;DR states the transport split and the fail-small posture in plain terms.
- **D20 — Sources are adapters; selection is a first-class choice.** `sources.active` and the menu picker (Section 4) treat "which trend source(s) feed this run" as an explicit decision, not a hardcoded assumption, so Google Trends/Hacker News slot in later without touching engine internals.
- **D21 — Virlo's MCP wrapper ships as Python, not Node.** *(Premise updated 2026-08-09: an official Virlo MCP server now exists with headless Bearer auth — Section 3 — so the wrapper is a deliberate choice for surface minimalism and churn insulation, not a necessity.)* Shipping it as a thin Python module in the same venv (Section 3) avoids introducing a second language runtime into a project whose entire premise is leanness, keeps the G2 line budget lean (00-overview.md), and makes the five-tool contract — plus its error translation, session-pool bound and retry behavior — an explicit, reviewable part of this PRD rather than an implicit assumption. Because we write the server ourselves, its tool names are fixed by that contract, which is why the config-driven tool-name map originally specified as FR-116 was withdrawn: a rename layer for five tools with exactly one implementation is generality with no consumer. The swap path to an official Virlo server survives intact at the level that actually matters — point `mcp_servers` at a different command.
- **D22 — Reel audio in-model, default ON.** Seedance 2.5 generates synchronized AI audio natively via a single `generate_audio` boolean (Section 8a) — no ffmpeg, no separate audio pipeline, no stitching step. Matches the project's "no ffmpeg" posture (D10) while still shipping reels with sound by default; turning it off per config ships silent clips for platform-native sound overlay instead.
- **D23 — withdrawn (v2.0.0, operator decision).** Viral-video motion references removed entirely per operator decision 2026-08-12. Reels render from seed frame and style references only (seed_frame_only is now the default and only option); yt-dlp dependency removed from project; motion-reference upload chain deleted from Section 8b; FR-160–FR-163 withdrawn. The seed frame's sufficient fidelity for reel text (FR-24) is unchanged.
- **D28 — withdrawn (v1.6.1; restatement re-based v2.0.0).** The declared media-richness property and text-grounded mode were pre-built machinery for adapters that don't exist. The old `text_only` item flag is withdrawn with the pivot: every post-pivot source is text-only by design, so a future adapter needs no such marker — its items enter the same topic pipeline as Virlo's (Section 4; `10-pipeline.md` FR-148/FR-149 tombstone).
- **D29 — Postiz is the committed Phase 2 target, spec'd now from live research, not left as a design sketch.** Rather than ship a "TBD, verify at build" placeholder, Postiz's actual MCP and REST surfaces were researched and verified before this amendment — the honest transport verdict in Section 6 and the full flow in `60-publishing-postiz.md` replace speculation with a plan that is implementation-ready; only its build is sequenced after MVP.
- **D30 — Secrets hygiene is absolute.** API keys are high-value, easy-to-leak strings, and this project logs everything (full prompts, full payloads) for debuggability — a combination that demands an explicit rule. Keys never enter a prompt or template, never reach a model, and are stripped from logs as a backstop even though they should never appear there in the first place (Section 9, NFR-112). This is a project-wide constraint owned here at the integration boundary where every key is actually used, and enforced at the logging boundary owned by `40-outputs-and-logging.md` (FR-152).
- **D34 — Model ids are config strings; render providers sit behind a four-operation seam; every render model carries a profile.** The model market turns over faster than this codebase will, and the old system's lesson was that model assumptions baked into code become the thing you cannot change. Keeping ids in config costs nothing — both model APIs are single-endpoint services where the id *is* the only difference between one model and another (Section 12), so the alternative would be hardcoding for no benefit. The seam is deliberately four operations wide: submit, poll, fetch results, upload. That is the smallest surface that still hides a vendor, and it is exactly the surface Kie already presents, so it costs a thin wrapper rather than an abstraction layer — a real consideration against the G2 line budget (00-overview.md). Profiles are what keep a swap honest: an id without a parameter mapping, a reference limit, and a prompt style is a promise the engine cannot keep, which is why an unknown profile refuses at **pre-flight (exit 2)** instead of failing halfway through a paid batch — the same posture as a malformed config value. The payoff is stated as a test rather than an aspiration: adding a model family must not touch Generate, the polling loop, or budget accounting (FR-273). Higgsfield.ai was the first real trial of this seam and it earned a "not yet" (Section 12a) — the seam's value is that the answer can change later without the pipeline noticing.
- **D35 — Transcript tactics: one is a brief, two are parked behind the seam** *(premise updated 2026-08-09)*. Three techniques surfaced from the operator's transcripts and were dispositioned rather than absorbed. *Product-photo-to-ad* needs **zero new machinery** — it is a worked campaign-brief example on existing D26 mechanics (brief-supplied reference images already upload through the FR-244 path), so it ships as documentation, not code. *Extension chaining* and *audio-reference music videos* stay **named future capabilities, explicitly parked — now by choice, not impossibility**: Kie's own Seedance 2.5 route exposes both primitives today (`return_last_frame` for shot chaining, `reference_audio_urls` for audio-guided generation — Section 8a), so promoting either later is config + prompt-template work behind the D34 seam, with no new provider needed. They stay out of the MVP because they are new *creative product surface* (multi-shot narratives, music-driven edits), not because the API is missing — and shipping them well needs template craft and evaluation that would dilute the MVP.
